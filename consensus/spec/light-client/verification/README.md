# Core Verification

This page describes the classic Tendermint light-client trust model retained in
this fork and maps it to the Go implementation. The original research versions
remain in [the published specification](verification_001_published.md),
[the second draft](verification_002_draft.md) and
[the third draft](verification_003_draft.md). Their pseudocode and proof sketches
are historical design material; the implementation links below define the
available API.

## Current network applicability

Paxeer is one network, run by `paxd`, with EVM chain ID 125 (`0x7d`). The kernel
runs within the node through [the cgo host](../../../../modules/lxphost/host.go)
and participates in the network's execution and block proposal path. A receipt
is final once its block is committed.

The verification model on this page requires classic signed headers and
validator-set commits. Check the consensus mode before choosing a provider:

- The node's `autobahn-config-file` setting in
  [the configuration](../../../config/config.go) selects Autobahn when non-empty;
  an empty value disables Autobahn.
- A classic commit is not an Autobahn certificate: the [consensus Commit handler](../../../internal/rpc/core/blocks.go)
  returns `coretypes.ErrCommitNotAvailable` when Autobahn is enabled. The
  [HTTP light provider](../../../light/provider/http/http.go) obtains signed
  headers through that handler, so this provider cannot bootstrap classic
  verification from an Autobahn node.
- Autobahn has committee-bound `CommitQC` and `FullCommitQC` types in
  [its certificate implementation](../../../autobahn/types/commit_qc.go).
  Their verification checks proposals, quorum signatures and, for full
  certificates, the supplied lane headers. These are different objects from
  `types.Commit` and `types.SignedHeader`.
- Autobahn restart safety uses persisted votes and quorum certificates in
  [the persisted consensus state](../../../internal/autobahn/consensus/persisted_inner.go)
  and [its persistence implementation](../../../internal/autobahn/consensus/persist/).
  The trusted-header reasoning below does not establish those recovery
  properties or provide an Autobahn light-client protocol.

The [specification index](../../README.md) provides the surrounding protocol
material. The following sections retain the Tendermint assumptions explicitly;
they do not claim current-network qualification for the archival models.

## Problem statement

A light client starts with a header `inithead` whose provenance it trusts and
wants to authenticate another header `newhead`. Its initial trust cannot be
created by downloading a header from the same untrusted provider it intends to
check. In the classic model, `inithead` must have been generated by Tendermint
consensus on the intended chain.

[TrustOptions](../../../light/trust_options.go) supplies `Period`, `Height` and
`Hash` for initialization. Basic validation requires a positive period and
height, and a hash of the required cryptographic size. These checks validate the
parameters' shape; the caller remains responsible for obtaining a trustworthy
checkpoint.

### Failure Model

For the retained research model, let `validators(hash)` denote the validator
set committed by a header hash. For a correctly generated header `h`, assume
validators holding more than two thirds of the voting power in
`validators(h.NextValidatorsHash)` remain correct until
`h.Time + TRUSTED_PERIOD`. Correctness is measured over real time, whereas
`Header.Time` is [classic BFT time](../../consensus/bft-time.md).

The model also assumes a bounded difference between the client's clock and
block time. Forward verification requires a new header's time to be strictly
before `now + maxClockDrift`. The Go client's `MaxClockDrift` option defaults to
10 seconds; the earlier research discussion of millisecond clock drift is not
a runtime default. A trusted header expires at equality:
`h.Time + trustingPeriod <= now`.

The trusting period must leave time for verification, evidence submission and
punishment within the unbonding period. It is an operator-supplied security
parameter, not a fixed number of weeks established by this page. The design
assumes `TRUSTED_PERIOD` is much larger than clock uncertainty. Basic parameter
validation does not prove the validator-honesty or clock assumptions.

If the failure model is violated, for example by at least one third faulty
voting power, this argument no longer guarantees safety. The retained
[fork-accountability discussion](../accountability/README.md) describes the
classic evidence model; it does not establish an Autobahn evidence contract.

### High Level Solution

Classic verification extends trust in three ways:

1. **Adjacent headers.** Authenticate the next height with the validator-set
   hash committed by the trusted header and a commit signed by more than two
   thirds of the new set's voting power.
2. **Skipping headers.** While the trusted header is unexpired, require enough
   signatures from its trusted validator set on the candidate commit, then
   check a greater-than-two-thirds commit under the candidate's validator set.
3. **Intermediate headers.** If the trusted set has insufficient overlap with
   the candidate's signers, fetch an intermediate light block, verify it, and
   use it to advance toward the target. Insufficient overlap alone does not
   prove that the provider forged a header.

## Definitions

### Data structures

The implementation uses the types in [light.go](../../../types/light.go),
[block.go](../../../types/block.go) and
[validator_set.go](../../../types/validator_set.go):

| Type or field | Role in classic verification |
| --- | --- |
| `Header.ChainID`, `Height`, `Time` | Chain identity, height and block time |
| `Header.LastBlockID` | Hash linkage to the previous block |
| `Header.ValidatorsHash` | Commitment to the current validator set |
| `Header.NextValidatorsHash` | Commitment to the next validator set |
| `SignedHeader` | Header paired with its `Commit` |
| `ValidatorSet` | Validators with addresses, public keys and voting power |
| `LightBlock` | `SignedHeader` paired with its current `ValidatorSet` |

`LightBlock.ValidateBasic` checks structural consistency, including the
validator-set hash, but does not verify cryptographic signatures. The client
stores verified light blocks through [the trusted-store interface](../../../light/store/store.go).
The old `TrustedState` pseudocode is not a Go API and must not be used to infer
that every stored block contains the next height's validator set.

### Functions

The pure verification functions live in [verifier.go](../../../light/verifier.go).
They take supplied headers, validator sets, timing parameters and, where needed,
a trust fraction. They do not fetch blocks or persist trusted state.

**Forward verification.** `Verify` dispatches to `VerifyAdjacent` for height
`trusted.Height + 1` and to `VerifyNonAdjacent` otherwise. Both paths reject an
expired trusted header and validate the candidate's signed-header structure,
chain ID, increasing height and increasing time. They also check the strict
future-time bound and the supplied validator set against `ValidatorsHash`.

`VerifyAdjacent` additionally requires the candidate's `ValidatorsHash` to equal
the trusted header's `NextValidatorsHash`, then verifies the candidate commit
with `ValidatorSet.VerifyCommitLight`.

`VerifyNonAdjacent` first validates `trustLevel`, then uses
`trustedVals.VerifyCommitLightTrusting` to check the candidate's commit against
the supplied trusted set. Insufficient overlap returns
`ErrNewValSetCantBeTrusted`; other commit failures return `ErrInvalidHeader`.
Only after the overlap check succeeds does it verify a greater-than-two-thirds
commit with the candidate's validator set.

`DefaultTrustLevel` is the rational fraction `1/3`. `ValidateTrustLevel` accepts
fractions in `[1/3, 1)`, rather than the old pseudocode's floating-point range.
The [commit verification implementation](../../../types/validation.go) requires
signed voting power strictly greater than the integer threshold
`totalPower * numerator / denominator`; equality is insufficient. The full-set
light check likewise requires more than `totalPower * 2 / 3`. Light verification
may stop once sufficient valid signatures have been counted; it does not
promise to validate every remaining signature in a commit.

**Downloading and verifying a target.**
`Client.VerifyLightBlockAtHeight(ctx, height, now)` in
[client.go](../../../light/client.go) is the implemented high-level entry point.
It rejects non-positive heights, returns a stored block if already trusted,
or downloads a light block from the primary and verifies it. Successful new
verification updates the trusted store. A cached return does not perform a new
expiry check; storing an authenticated historical block is distinct from using
it as an unexpired forward trust anchor.

The HTTP provider calls the consensus client's `Commit` and `Validators`
methods, checks the returned height and chain, and constructs a `LightBlock`.
These are consensus RPC operations. The EVM chain ID 125 does not replace the
consensus `Header.ChainID` string checked by the verifier, and an Ethereum JSON-RPC
endpoint alone does not supply this provider contract.

**Skipping and intermediate selection.** The default client mode is
`SkippingVerification(DefaultTrustLevel)`; `SequentialVerification()` requests
verification through every intervening height. The skipping implementation
caches fetched light blocks and seeks an intermediate only on
`ErrNewValSetCantBeTrusted`. Other verification errors abort that attempt.
Its scheduler chooses
`trustedHeight + (failedHeight - trustedHeight) * 9 / 16`
using integer arithmetic, rather than the research draft's recursive midpoint.
The client also compares the resulting trace with witnesses to detect
conflicting histories. That detection assumes at least one correct full node
among the primary and witnesses; see the [detection material](../detection/README.md)
for the retained research context.

**Errors.** The implemented verification errors are declared in
[errors.go](../../../light/errors.go):

| Error | Meaning and response |
| --- | --- |
| `ErrOldHeaderExpired` | The forward trust anchor expired; obtain a fresh trusted checkpoint. Expiry alone does not establish provider misconduct. |
| `ErrNewValSetCantBeTrusted` | Insufficient trusted voting-power overlap; skipping verification can try an intermediate light block. |
| `ErrInvalidHeader` | Invalid header, validator linkage or commit; do not advance trust using it. |
| `ErrVerificationFailed` | A higher-level attempt failed between specified heights; inspect its wrapped reason. |

Provider failures and context cancellation are additional error cases. An error
is not automatically proof of a forged header. The client distinguishes
provider replacement, insufficient overlap and expiry; callers must not accept
a failed result as newly trusted.

### The case `untrustedHeader.Height < trustedHeader.Height`

Backward authentication follows hashes from an already trusted later header.
`VerifyBackwards(untrustedHeader, trustedHeader)` validates the older header's
basic structure, matching chain ID, strictly earlier time and hash equality
with `trustedHeader.LastBlockID.Hash`. It does not check trust-period expiry or
verify commit signatures. This differs from the historical
`VerifyHeaderBackwards` pseudocode, which included expiry checks.

The client's `backwards` method fetches each preceding height, applies
`VerifyBackwards` and checks that the final authenticated hash matches the
requested target. It limits a traversal to 10,000 headers. A hash link
establishes historical ancestry; it does not renew the older header as a
forward trust anchor.

When a requested height lies between the earliest and latest stored trusted
blocks, the client selects the closest stored block before the target and
verifies forward. It does not choose arbitrarily between forward and backward
verification as the original research note suggested.

## Correctness of the Light Client Protocols

### Definitions

In the retained model, a validator is a pair `(v, p)` of unique identity and
voting power. Write `correct(v, t)` when validator `v` follows the protocol
through real time `t`, and `trust(h)` when a client accepts header `h` under the
model's assumptions. Voting-power sums, rather than validator counts, determine
the classic quorum conditions.

### Failure Model and verification conditions

For a correctly generated header `h`, the assumption is:

```text
sum(p for (v, p) in validators(h.NextValidatorsHash)
    if correct(v, h.Time + TRUSTED_PERIOD))
  > (2/3) * sum(p for (v, p) in validators(h.NextValidatorsHash))
```

The research goals are **accuracy**, accepting only correctly generated classic
headers, and **completeness**, eventually authenticating correctly generated
headers while the necessary trust anchors remain usable. Completeness depends
on available correct providers, sufficient time and reachable intermediate
headers; it is not a promise that an arbitrary remote node will respond.

Starting from a genuine trusted checkpoint, the intended invariant is that
acceptance preserves the failure-model assumption for subsequent trust
transitions. This is a conditional correctness argument, not proof that the
assumptions hold for a particular deployment or that the archival models cover
Autobahn.

## Details

**Why overlap matters.** If less than one third of trusted voting power is
faulty, a valid commit carrying signatures from more than one third of that
trusted power includes a correct signer. Together with the classic protocol
assumptions, validator-set commitments and the candidate's greater-than-two-thirds
commit, this supplies the forward trust argument. Trust in a set does not mean
every individual member is honest.

**Adjacent progress.** The trusted header commits to the next validator set.
Matching that commitment and verifying the next height's commit avoids the
additional old-set overlap requirement used for skipping.

**Skipping progress.** Each successful intermediate verification extends the
trust path. Raising the trust fraction increases the overlap required, so it
can cause more intermediate requests or verification failure when membership
changes quickly. It does not make skipping more likely to succeed. Each step
still needs a usable trust anchor and a correctly authenticated commit.

**Time and stalling.** A faulty or unavailable provider can delay completion
without producing an invalid header. Use a context deadline, appropriate
provider timeouts and independent witnesses, and obtain a fresh checkpoint
when the forward anchor expires. The implementation has retries and provider
replacement; the research suggestion of moving bisection to a server is not an
implemented protocol guarantee. None of these classic light-client arguments
replaces Autobahn certificate verification or durable consensus recovery.
