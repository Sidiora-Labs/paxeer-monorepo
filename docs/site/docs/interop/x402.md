# x402 transport

`layerx-x402` implements buyer, seller and facilitator roles for x402 v2.
The adapter id is `x402`, its specification version is `2.0.0`, and the
upstream pin is `7d5363a6d51750dc246041f2b0ed5819dd46a0d7`. The compiled
document is `services/interop/specs/vendor/x402/x402-specification-v2.md`.

Paxeer is one BFT network with EVM chain id `125` (`0x7d`); the kernel runs
inside the network and proposes blocks. The payment profile uses
`eip155:125`. Payment execution is a native transaction, and a receipt becomes
final when its block is committed. Adapters translate commerce messages and
verify evidence; they do not write balances.

This page covers the Rust adapter in `services/interop/crates/layerx-x402`,
its interop service wrappers and their implementation limits. Related commerce
adapters are [UCP](ucp.md) and [Visa TAP](visa-tap.md).

## Payment-required flow

1. The seller issues HTTP `402` with a validated `PaymentRequired` value in
   the body and its standard-base64 JSON in `PAYMENT-REQUIRED`.
2. The buyer selects the first seller-ordered offer whose `(scheme, network)`
   is supported. `BuyerPaymentPlane::construct` supplies an object payload;
   the buyer preserves the selected offer and required extensions in
   `PAYMENT-SIGNATURE`.
3. The seller or facilitator validates the accepted offer, extension echo
   and stable payment identity. `/verify` checks the request without
   submitting it; it is not payment settlement.
4. The payment plane submits the signed native transaction through
   `eth_sendRawTransaction` and recovers its evidence by transaction hash
   with `pax_sequencerReceipt`. The adapter verifies the receipt and payment
   logs before the gateway records `TranslationStatus::ReceiptVerified`.
5. The seller returns `PAYMENT-RESPONSE`. The buyer independently verifies
   the response against its original offer, payment identity and trusted keys
   before treating the payment as accepted. Finality requires committed
   evidence as described below.

### Node transport and service boundaries

Public node JSON-RPC uses HTTPS at the root, for example
`https://api1.mainnet-beta.paxeer.network` or
`https://api-mainnet-beta.paxeer.network`. The numbered pool is `api1` through
`api14.mainnet-beta.paxeer.network`; see [public RPC endpoints](../reference/public-rpc.md).
Confirm `eth_chainId == "0x7d"` before signing. For example:

```bash
curl -sS https://api1.mainnet-beta.paxeer.network \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'
```

`pax_sequencerReceipt` and the governed key read `px_getReceiptKeys` are
implemented by the node. The gateway also exposes the key list under
`services/platform/hosted/gateway/openrpc.json`. Method availability and key
state depend on the serving deployment. The interop service uses its configured
upstream and compares published receipt keys with deployment pins at startup. Public
chain access, hosted gateway calls and the interop HTTP wrappers have distinct
contracts. Sub-chains are tenant domains in the database and do not change
the public EVM chain id.

### Hosted exact-payment payload

The current interop service's verify and settle planes read these fields
from the x402 `payload` object:

| Field | Meaning |
| --- | --- |
| `layerxTransaction` | Hex-encoded, payer-signed EIP-1559 transaction |
| `layerxIdempotencyKey` | 32-byte hexadecimal payment reference, preserved across retries |
| `transaction` | Native transaction hash; the facilitator's verify entry point requires its canonical `0x`-prefixed form |

The transaction must target ledger precompile
`0x000000000000000000000000000000000000101a` and call `payExact` (selector
`0x78ea11db`). Its six ABI words are `from`, `to`, `asset`, `amount`,
`expiresAt` and `reference`; the service decodes `amount` as `u128` and
`expiresAt` as `u64`, refusing nonzero high padding. It recovers the EVM
signer, checks the destination, asset and exact amount against the offer,
checks expiration, and requires the reference to equal
`layerxIdempotencyKey`. An activity-only payload cannot substitute for this
signed transaction.

Native transaction verification requires the payment reference to equal
`layerxIdempotencyKey`. Final receipt matching also requires it to equal the
derived `SettlementIdentity::idempotency_key`, which binds the principal,
caller identity and settlement step. The hosted wrapper returns success only
when both checks pass. A verify response alone does not establish settlement;
preserve the signed transaction under its original operation identity.

The service's buyer-build route wraps a supplied object payload; the payer's
wallet or payment authority constructs and signs the transaction. A
successful verify response does not establish balance availability or receipt
success. Those are decided on the native payment path.

## Offer and payload contract

`PaymentRequirements` contains `scheme`, `network`, `amount`, `asset`,
`payTo`, `maxTimeoutSeconds` and optional `extra`. Amounts are canonical
decimal JSON strings and exact `u128` in Rust. Signs, fractions, exponents,
padded strings and overflow are refused. An offer requires a positive amount
and positive timeout; parsing an amount alone also permits zero.

For `eip155:125`, `asset` and `payTo` are 32-byte hexadecimal identifiers,
with an optional `0x` prefix in the Rust model. `payTo` is a protocol account
id, not the 20-byte ledger precompile address. The offer must include
`extra.layerx.account` and `extra.layerx.currency`:

- `account` is `agent:<did>:main` or `agent:<did>:asset:<asset>`. A per-asset
  reference must contain the lowercase 64-hex id of this offer's asset.
- `currency` is a nonempty uppercase ASCII letter/digit code of at most
  16 bytes. It is quote metadata, not a substitute for the exact asset amount.
- `payTo` must equal one of the account identifiers returned by
  `account_identifiers(account)`: `SHA256("LXP/v1/account-id\0" || name)` or
  `SHA256("LX:ACCOUNT:v1" || u32be(len(name)) || name)`, over the UTF-8 bytes.

Missing terms are `ProfileMissing`; malformed terms or a different derived
payee are `ProfileMismatch`. The Rust model validates this payment profile
specifically on `eip155:125`. General CAIP-2 syntax validation does not imply
support for a different network's settlement.

`PaymentPayload.accepted` must equal an issued offer. Required extensions
must be preserved by value and the scheme payload must be a JSON object.
The Rust wire models use camelCase names and reject unknown struct fields.

## 402LXP Asset grants

The adapter's receipt matcher recognizes `exact`, `metered` and `subscription`.
Exact payments bind a `PaymentExact` log. Metered and subscription evidence
binds a `PaymentDrawn` log, the payload's `grantId`, recipient, asset, exact
amount and payment idempotency reference. Grant offers must supply a lowercase
64-hex `extra.layerx.purposeHash`; settlement echoes that purpose, and buyer
capture requires it to equal the original offer's purpose.

This evidence support does not make grant-based payments available on the
current chain. The ledger's `IssueGrant`, `RevokeGrant` and `Draw` paths
refuse payer grants (`ErrNoPayerGrant` after applicable pause and authority
checks); the hosted interop plane decodes `payExact`
transactions only. Do not advertise metered or subscription settlement on
that plane merely because a wire message parses. Consult the configured
facilitator's `/supported` declaration and its actual payment plane.

Platform middleware under `services/platform/middleware/` also validates
metered/subscription offer terms, including nonzero payer and purpose hashes.
Subscription requires a positive decimal `windowSeconds` fitting `u64`;
metered forbids that field. Its commitment vocabulary is `receipted` or
`committed`. An embedding selects its offer-validation and commitment
policy before fulfillment, in addition to the Rust model's wire validation.

Keep one stable request identity per charge. A recurring authorization alone
cannot prove that a subscription period was charged exactly once. The former
ordinal-7 payer-grant and ordinal-6 receive instructions are retired and are
not a submission recipe for the merged network.

## Header and body encodings

| Header | Core value |
| --- | --- |
| `PAYMENT-REQUIRED` | `PaymentRequired` |
| `PAYMENT-SIGNATURE` | `PaymentPayload` |
| `PAYMENT-RESPONSE` | `SettlementResponse` |

HTTP payment signals use serde JSON followed by RFC 4648 standard base64.
The decoded JSON limit is `64 * 1024` bytes. Decoding also refuses an empty
header or header text longer than twice that limit. MCP and A2A payment
signals carry the same validated JSON objects as `TransportValue::Json`,
with the same JSON byte limit. A transport/value or header-name mismatch is
refused.

Facilitator `/verify`, `/settle` and `/supported` messages use JSON bodies
on all three transports. They are distinct from the payment-signal headers.
`transport.rs` supplies the transport-neutral encoders; the convenience
`Seller::payment_required` method always produces the HTTP header form.

## Roles

| Role | Boundary |
| --- | --- |
| Seller | Validate the issued offer and returned payload; execute through `PaymentPlane`; verify native receipt and payment facts before success |
| Buyer | Construct through `BuyerPaymentPlane`; independently capture evidence with pinned receipt keys and, for commitment, trusted consensus anchors |
| Facilitator | Advertise supported kinds; keep `FacilitatorPlane::verify` read-only; settle through the same receipt-gated seller path |

The interop gateway registers the following paths for each transport `t`
in `http`, `mcp`, `a2a`. These paths use the configured interop origin.

| Method | Path |
| --- | --- |
| `GET` | `/v1/{t}/x402/supported` or `/v1/{t}/x402/facilitator/supported` |
| `POST` | `/v1/{t}/x402/buyer/build` |
| `POST` | `/v1/{t}/x402/seller/offer` |
| `POST` | `/v1/{t}/x402/verify` or `/v1/{t}/x402/facilitator/verify` |
| `POST` | `/v1/{t}/x402/settle`, `/v1/{t}/x402/seller/settle` or `/v1/{t}/x402/facilitator/settle` |

`X402Settle` is the only state-changing x402 route. The service dispatches
settle aliases through its facilitator, requires an API key, and derives
the stable settlement identity from the payment reference. It returns HTTP
`202` for a pending transaction, HTTP `200` with the settlement response for
settled or refused plane outcomes, and typed HTTP errors for unavailable or
invalid requests. Inspect `success` and evidence, not just the HTTP status.

## Receipt binding

`ExecutedPayment` contains `SequencerEvidence` and an optional
`CommittedSettlementProof`. `SequencerEvidence` owns `transaction_hash`,
`signed_receipt`, `logs` and `rung`:

| Rung | Meaning and acceptance |
| --- | --- |
| `submitted` | Transaction known; no receipt-backed success. Facilitator response has `success: false`, `errorReason: "settlement_pending"`, the transaction hash and `verificationLevel: "submitted"` |
| `receipted` | Successful native receipt and payment logs verified under pinned sequencer keys; block commitment has not been proven |
| `committed` | The same receipt plus verified consensus commitment and inclusion evidence, with matching block number and block hash |

Seller settlement verifies canonical receipt encoding and its Ed25519
signature through `verify_sequencer_signature` using
`ReceiptKeys::HeightRanges`. Keys are `SequencerAuthorization` entries pinned
by identity and authorized height range. They come from trusted deployment
configuration, never from the payment being verified. A single historical
kernel key is insufficient for a native receipt.

The seller requires `result_code == 0`, binds the receipt's transaction id
to `evidence.transaction_hash`, and verifies served logs against the signed
effects with `verify_logs`. Exactly one relevant ledger payment event must
match the accepted payment facts and idempotency key. For committed evidence,
`verify_committed` must verify the same signed receipt and the claimed block.
`GatewayCore::settle_with_sequencer_evidence` independently verifies receipt,
logs and payment-reference matching, then records the canonical receipt
digest. The gateway record alone does not prove consensus commitment.

Successful `SettlementResponse` fields are:

| Field | Value |
| --- | --- |
| `success` | `true`, with no `errorReason` |
| `transaction` | Nonzero 32-byte transaction hash as `0x` plus 64 lowercase hex digits |
| `network`, `amount` | Accepted network and exact decimal-string amount |
| `payer` | 32-byte payer from the verified payment log, encoded as unprefixed hex |
| `extensions.layerx.receipt` | Standard-base64 canonical signed receipt |
| `extensions.layerx.receiptDigest` | Unprefixed hexadecimal canonical receipt digest |
| `extensions.layerx.verificationLevel` | `receipted` or `committed` |
| `extensions.layerx.logs` | Verified logs with `address`, `topics`, `data` and hexadecimal `logIndex` |
| `extensions.layerx.purposeHash` | Original offer's purpose for metered/subscription settlement |
| Committed-only fields | `extensions.layerx.blockNumber` as a hex quantity, `blockHash` as a prefixed hash, and `proof` |

The digest is computed by `canonical_receipt_digest`; it is distinct from the
transaction hash. The former `lxp:<receipt_digest>` transaction identity is
retired and rejected by native settlement.

`Buyer::capture_settlement` re-verifies the receipt, logs, transaction hash,
digest, network, payer, amount, recipient, reference and applicable purpose.
It accepts receipt evidence but refuses committed claims without an
independently trusted consensus anchor. For commitment, use
`capture_settlement_with_consensus` or a buyer configured with
`TrustedConsensusAnchor` values for the offered network. Advance an anchor
through verified signed successors when validator sets change; validators
supplied by a response alone cannot authorize that response's chain.

The current hosted interop settle plane returns `SequencerEvidence` without
providing `FacilitatorCommitment`. Therefore it cannot produce a successful
committed x402 response through the proof-requiring adapter path. Consumers
requiring finality must obtain and verify the full commitment evidence;
they must not relabel a receipted response as committed.

### Retry and recovery

`SettlementIdentity::derive` excludes transport and separates `Single`,
`EscrowDeposit` and `EscrowCharge` steps. Gateway state is scoped to the
authenticated principal. Reusing an identity with changed request content or
settling it on another receipt digest conflicts; retrying the same verified
digest returns the existing result.

The service's `ChainRelay` journals the signed transaction bytes and hash
before submission. Recovery looks up the original hash and, when unknown,
can resubmit those same bytes. Replacing the bytes under the same identity
is refused. Preserve the request, reference, signed transaction and evidence
across timeouts and restarts; do not create another payment to escape an
uncertain response. Fulfillment should durably bind the request identity and
unique payment evidence so redelivery cannot fulfill a different request.

## Typed refusals

These are Rust `X402Error` variants, not JSON-RPC numeric codes:

| Refusal | Meaning |
| --- | --- |
| `Decode`, `Encode`, `Bounds`, `WrongVersion` | Malformed representation, serialization failure, exceeded bound or version other than `2` |
| `InvalidAmount`, `InvalidRequirements`, `InvalidPayload` | Noncanonical amount, invalid offer or invalid payload shape |
| `ProfileMissing`, `ProfileMismatch` | Missing account/currency terms or terms that fail the payment profile binding |
| `UnsupportedOffer`, `RequirementsMismatch`, `ExtensionsMismatch` | Unsupported kind, changed accepted offer or missing/changed required extension |
| `TransactionForm` | Invalid settlement transaction-hash representation |
| `PaymentRefused` | Payment plane refusal or unsuccessful response at buyer capture |
| `EvidenceMissing`, `EvidenceMismatch` | Absent proof, bad signature, wrong payment facts, untrusted commitment or inconsistent evidence |
| `Gateway(_)` | Registration, translation, idempotency or gateway settlement failure |

Pending is an explicit seller/facilitator outcome; it cannot be converted to
success. Safe plane reasons contain only lowercase ASCII and `_`, with
length `1..=64`; other reason strings are rendered as `payment_refused`.
The service's native decoder distinguishes `transaction_malformed`,
`transaction_target_refused`, `transaction_selector_refused` and
`transaction_signature_refused`. Offer/reference/expiry failures include
`payment_requirements_mismatch`, `protocol_idempotency_mismatch` and
`activity_time_window_refused`. A transport or parsing error is not evidence
that the payment is pending or failed on chain.

## Conformance vectors

First-party x402 vectors are loaded from
`services/interop/specs/conformance/x402/`; transport vectors are under
`services/interop/specs/conformance/transport-{http,mcp,a2a}/`.
The crate's `tests/vectors.rs` and `tests/transports.rs` exercise wire
validation, encode/decode parity, settlement identity, duplicate delivery
and recovery. Additional evidence tests cover native payment logs, receipt
key pins and independently anchored commitment proofs.

These are local suites. They do not establish interoperability with an
independently operated facilitator or live public-service settlement.
`services/interop/crates/layerx-x402/COMPATIBILITY.md` describes the matrix's
scope. The [portable verification guide](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/main/docs/interop/PORTABILITY.md)
describes offline receipt verification and its trust boundaries.

## `make interop-test-x402`

The repository target runs the `layerx-x402` package's tests through the
interop Cargo workspace. It is the adapter's test entry point, not a live
merchant or cross-protocol qualification gate.
