# Paxeer 7.0.0 rollback and recovery

This page covers release `paxeer-network/v7.0.0` and upgrade plan `v7.0`.
Use it with the [validator runbook](7.0.0-validator-runbook.md) and the
[merged-network runbook](../runbooks/paxeer-x-fork.md). Before the upgrade,
governance can cancel the plan. Once the upgrade height is reached, keep the
node's data and newest signing state intact. The release rollback script refuses
a snapshot restore on the same chain; live recovery uses a compatible binary
with the current data.

Commands run from the repository root. `H` means the governance upgrade height.
`PAXD_BIN`, `PAXD_HOME`, `PAXD_UNIT` and `COMET_RPC_URL` have the meanings in the
validator runbook. `ROLLOUT_ENV` is the path to the operator's private release
input file, based on `tools/release/env/rollout.env.example`. `BIN_DIR` and
`RELEASE_ID` in shell commands must match that file. Keep filled inputs and
backups in access-controlled storage.

## Before the upgrade height

Keep the running binary, its SHA-256, its runtime libraries and its configuration
before replacing anything. Keep stopped copies of configuration, genesis, node
and validator keys, the newest local and remote signing state, all PaxDB
directories and the sequencing WAL. Include external storage configured by
`state-commit.sc-directory`, `state-store.ss-db-directory`,
`state-store.evm-ss-db-directory` and `sequencer.wal-dir`. Keep exactly one active
signer for each consensus key.

The two installation layouts use different filenames:

| Installation | Staged binary | Retained earlier binary |
| --- | --- | --- |
| Manual validator runbook | `$PAXD_BIN.v7.0` | `$PAXD_BIN.pre-v7.0` |
| `tools/release/stage.sh` | `$BIN_DIR/paxd.v7.0.0` | `$BIN_DIR/paxd.pre-$RELEASE_ID` |

`stage.sh --local --env-file "$ROLLOUT_ENV"` preserves the installed `paxd`
under the retained name if that file is absent, and installs the release beside
it. It leaves the installed `paxd` in place. Preserve the retained file across
subsequent staging operations and keep its checksum separately. Check that its
shared libraries remain available:

```sh
sha256sum "$BIN_DIR/paxd.pre-$RELEASE_ID"
ldd "$BIN_DIR/paxd.pre-$RELEASE_ID"
```

For release asset validation, `tools/release/verify-release.sh` compares the
published asset names, checksums and contents with a local release directory:

```sh
tools/release/verify-release.sh --tag paxeer-network/v7.0.0 \
  --dist dist/paxeer-network/v7.0.0
```

To withdraw before `H`, have governance cancel the software upgrade and confirm
that the cancellation has taken effect:

```sh
"$PAXD_BIN" q upgrade plan --node "$COMET_RPC_URL" -o json
```

Require the `no upgrade scheduled` response; a query or transport error does not
confirm cancellation. The governance proposal command is
`tx gov submit-proposal cancel-software-upgrade` (see
`sdk/x/upgrade/client/cli/tx.go`). Removing a staged file does not cancel a plan.
After cancellation is confirmed, remove the staged file for the layout in use:

```sh
rm -- "$BIN_DIR/paxd.v7.0.0"
```

For the manual layout, use `rm -- "$PAXD_BIN.v7.0"` instead. Keep the installed
binary, retained binary and backups. `stage.sh` has no withdrawal option. If
using Cosmovisor, also withdraw its staged binary at
`$DAEMON_HOME/cosmovisor/upgrades/v7.0/bin/paxd`; keep
`DAEMON_ALLOW_DOWNLOAD_BINARIES=false` and
`DAEMON_RESTART_AFTER_UPGRADE=false` as described in the validator runbook.

## At the upgrade height

The governance path halts when the earlier binary reaches `H` without a `v7.0`
handler. It writes `data/upgrade-info.json`, emits
`UPGRADE "v7.0" NEEDED at height: H: ...` and panics before applying the upgrade.
The last committed application height is `H-1`. Restarting the same binary
reaches the same halt while the plan remains due (`sdk/x/upgrade/abci.go`).
There is no automatic binary replacement in a direct `paxd` start.

If the new binary is absent, cannot load its shared libraries, or cannot start,
the node does not resume block processing. Stop the service and fence automatic
restarts and remote signing:

```sh
systemctl stop "$PAXD_UNIT"
jq '{name, height}' "$PAXD_HOME/data/upgrade-info.json"
```

On the governance path, require name `v7.0` and height `H`. Preserve that file,
the databases, WAL and latest signing state. A signed proposal or vote can exist
even when its block never committed. Restoring an older signing-state file can
allow double signing. Keep the node stopped for a compatible repair binary if
startup or the upgrade handler refuses to proceed. Do not run the earlier binary
against migrated stores or use `--unsafe-skip-upgrades`; that option clears the
due plan without applying its migration (`sdk/x/upgrade/abci.go`).

The release scripts use a separate halt convention. `snapshot.sh` validates
validator signing state at `HALT_HEIGHT` (also accepting its recognized signed
halt proposal at `HALT_HEIGHT + 1`). `swap.sh` writes upgrade metadata for
`HALT_HEIGHT + 1` and resets `halt-height` in `config/app.toml` to zero. Thus a
scripted swap targeting governance height `H` uses `HALT_HEIGHT = H-1`; do not
pass `H` as the halt height. The validator runbook uses the governance halt and
manual swap, without setting `--halt-height` or `--halt-time`.

For a stopped script-layout node whose state satisfies those snapshot checks:

```sh
tools/release/snapshot.sh --env-file "$ROLLOUT_ENV"
tools/release/snapshot.sh --env-file "$ROLLOUT_ENV" --verify
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --readiness
```

The snapshot script archives only each home's `data` directory as
`$SNAPSHOT_DIR/<home-name>-pre-v7.0.0.tar.zst` and checks its contents. It does
not replace the separate backups of configuration, keys, external stores or WAL
outside `data`. `--readiness` checks retained material; it does not authorize or
perform a same-chain restore.

## After the upgrade height

Once `H` commits, recover the live network forward with a binary that understands
the committed state. A local snapshot restore cannot undo the network's commit.
Check the applied plan with:

```sh
"$PAXD_BIN" q upgrade applied v7.0 --node "$COMET_RPC_URL" -o json
```

For script-managed recovery, set `RECOVERY_BIN` to a separately staged,
canonical absolute binary path and `RECOVERY_SHA256` to its expected lowercase
SHA-256 in the private input file. The recovery binary must be outside
`$BIN_DIR/paxd` and `$BIN_DIR/paxd.new`. Keep `RELEASE_ID`, `HALT_HEIGHT`,
`BIN_DIR`, `SNAPSHOT_DIR`, home lists and matching unit lists in that file.
Use the same file and binary throughout recovery.

The following commands act only on the local homes. Stop the nodes first:
the execution preparation requires them already stopped. Fence any external
signer and automatic restart mechanism as well.

```sh
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --forward --readiness
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --forward \
  --execute --phase stop
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --forward --execute
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --forward --verify
```

Forward recovery retains the current `data`, checks that signing state does not
regress, resets `halt-height` to zero, checks binary linkage, atomically replaces
`paxd` and starts the configured units. Verification requires one matching binary
process per home, `catching_up = false`, and an increasing committed height above
`HALT_HEIGHT`. Repeat the validator runbook's post-upgrade checks before returning
traffic. `--service-manager foreground` is available with `--local`; it starts
`paxd start --home` and requires an empty `SIDECAR_UNITS` list.

### Returning to earlier binary and data on an isolated fork

`rollback.sh` permits snapshot restoration only with
`ROLLBACK_ISOLATED_FORK=true` and `ROLLBACK_SOURCE_GENESIS` pointing to the source
genesis. Every selected home must already have a different consensus chain ID,
fresh validator consensus identities disjoint from the source validators, and
its local key in the fork validator set. RPC and P2P listeners and persistent
peers must use loopback networking; peer discovery must be disabled, with empty
external address, bootstrap peers and seeds. Keep this fork isolated from the
live network.

With those conditions established, the earlier executable at
`$BIN_DIR/paxd.pre-$RELEASE_ID` and the checked snapshot archives are the restore
inputs. Stop the isolated nodes before execution:

```sh
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --readiness
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --execute --phase stop
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --execute
tools/release/rollback.sh --env-file "$ROLLOUT_ENV" --local --verify
```

Restoration retains the displaced data at
`<home>/data.v7.0.0-<RELEASE_ID>`, extracts and compares the earlier archive,
removes the restored `data/upgrade-info.json`, resets `halt-height` to zero and
atomically installs the retained executable through `$BIN_DIR/paxd.new`. It
does not rewrite genesis or cancel an upgrade plan stored in application state.
Successful startup and advancing heights depend on the fork's compatible state
and configuration. Verification requires the restored binary hash, advancing
heights above `HALT_HEIGHT` and no reappearing upgrade file. These commands do
not provide a way to rewind a validator on the live chain.
