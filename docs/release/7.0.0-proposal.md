# Paxeer 7.0.0 upgrade proposal

Release `paxeer-network/v7.0.0` uses the on-chain upgrade name `v7.0`.
The node registers this name as `MergeUpgrade` and schedules it through
governance. See the [upgrade plan](7.0.0-upgrade-plan.md),
[handler registration](../../node/upgrades.go) and
[plan constant](../../precompiles/common/precompiles.go).

The [example JSON](7.0.0-proposal.example.json) is an unsigned transaction
containing one `/cosmos.gov.v1beta1.MsgSubmitProposal` message. Its content is
`/cosmos.upgrade.v1beta1.SoftwareUpgradeProposal`, which carries the plan.
These are the types registered by this tree's
[governance codec](../../sdk/x/gov/types/codec.go) and
[upgrade codec](../../sdk/x/upgrade/types/codec.go).

The example requires replacement values before submission:

| Field | Replacement |
| --- | --- |
| `content.title`, `content.description` | Proposal text describing the release, height and binary identity |
| `content.plan.height` | Positive future height `H`; the example's `"0"` is a placeholder |
| `content.plan.info` | JSON string generated from the release binaries and sequencer inputs below |
| `initial_deposit` | Amount and denomination from current governance parameters; `0placeholder` is a placeholder |
| `proposer` | Proposing account selected by the CLI's `--from` option |
| Transaction fee, gas and signatures | Values produced by the transaction commands |

The zero SHA-256 digest and public-key strings are placeholders. The zero
`last_seq` and zero 32-byte `last_seq_hash` are required initial sequencer values.
The example's receipt-key range is illustrative; select the actual validity
range when generating plan info. Protobuf JSON represents the plan's signed
64-bit height as a decimal string. The sequencer fields inside `info` use JSON
numbers for heights.

## Choose the height

Query current governance parameters and any scheduled plan:

```sh
paxd query gov params --node "$COMET_RPC_URL" --output json
paxd query upgrade plan --node "$COMET_RPC_URL" --output json
```

`COMET_RPC_URL` is the configured CometBFT RPC endpoint. Set `PAXD_HOME` to the
node home and `COSMOS_CHAIN_ID` to the intended Cosmos chain ID. The commands
below use shell variables for account aliases, amounts, text and file paths;
set each to the intended value before use.

Choose a positive future `H` using the current chain height, measured block
interval, deposit period and voting period from the live parameters. Allow time
for the proposal to enter voting, pass and be applied, and for validators to
stage the release before `H`. Height determines execution; an estimated time
is only a scheduling aid. The upgrade keeper rejects heights in the past.
See [plan validation](../../sdk/x/upgrade/types/plan.go) and
[scheduling](../../sdk/x/upgrade/keeper/keeper.go).

At `H`, the upgrade handler activates the merged network. With
`activation_height` zero or omitted, the first sequenced height is `H + 1`.
At least one receipt key must cover `H + 1`; keys must also cover an explicitly
set activation height. The commands below keep `activation_height` zero.
The separate `v7.0-anchor-store-delete` plan uses its own later proposal.

## Produce the information field

Use the release binaries and their published `SHA256SUMS`. Check the downloaded
files against that manifest in the release directory:

```sh
cd "$RELEASE_DIR"
sha256sum --check --strict SHA256SUMS
```

From the repository root, generate the binary download information:

```sh
python3 tools/release/upgrade_info.py release \
  --sums "$RELEASE_DIR/SHA256SUMS" \
  --tag paxeer-network/v7.0.0 --name v7.0 \
  --out "$RELEASE_INFO_FILE"
```

`RELEASE_INFO_FILE` is an output path for the release document. The
[release tool](../../tools/release/upgrade_info.py) reads the
`paxd-v7.0.0-linux-amd64` checksum from the manifest and produces a document
with `name` and a JSON-encoded `info` string. Its `binaries["linux/amd64"]`
URL includes `?checksum=sha256:` followed by that checksum. It currently emits
this binary target. Checking the files against the manifest establishes their
agreement; obtain the manifest from the intended release.

The handler also consumes sequencer genesis from `plan.info`. Generate that
data and include the binary map:

```sh
python3 tools/release/upgrade_info.py plan-info \
  --leader "$LEADER_PUBLIC_KEY" \
  --receipt-key "$RECEIPT_KEY_JSON" \
  --plan-height "$H" --activation-height 0 \
  --release-doc "$RELEASE_INFO_FILE" --out "$PLAN_INFO_FILE"

python3 tools/release/upgrade_info.py plan-info \
  --check "$PLAN_INFO_FILE" --plan-height "$H"

python3 tools/release/upgrade_info.py release \
  --sums "$RELEASE_DIR/SHA256SUMS" \
  --tag paxeer-network/v7.0.0 --name v7.0 \
  --plan-info "$PLAN_INFO_FILE" --out "$COMBINED_RELEASE_INFO_FILE"
```

`PLAN_INFO_FILE` and `COMBINED_RELEASE_INFO_FILE` are output paths. The latter
contains the final `name` and escaped `info` string for the example's plan.
`PLAN_INFO_FILE` contains the same information as a raw JSON object for the
CLI's `--upgrade-info` option. The binary map alone does not supply the required
sequencer genesis.

Supply actual public values:

| Input | Encoding and meaning |
| --- | --- |
| `LEADER_PUBLIC_KEY` | Nonzero 32-byte consensus public key, as 64 hex digits or base64; repeat `--leader` for distinct leaders in primary-first order |
| `RECEIPT_KEY_JSON` | JSON object with `key_id`, `public_key`, `first_height` and `last_height`; repeat `--receipt-key` for additional entries |
| `key_id` | Unique nonzero 32-byte identifier encoded as base64 |
| Receipt `public_key` | Canonical 32-byte Ed25519 public key encoded as base64 |
| `first_height`, `last_height` | Positive inclusive numeric bounds; at least one entry covers `H + 1` |

The tool defaults `last_seq` to zero and `last_seq_hash` to the base64-encoded
zero hash. Receipt public keys are separate from consensus public keys. Supply
only public keys in the proposal. Changing `H` requires regenerating the plan
info so its recorded `plan_height` and receipt-key coverage agree.

## Submit, deposit and vote

The registered submission command is
`paxd tx gov submit-proposal software-upgrade`. It constructs the single
governance message shown in the example. Use the generated raw plan info:

```sh
paxd tx gov submit-proposal software-upgrade v7.0 \
  --upgrade-height "$H" --upgrade-info "$(cat "$PLAN_INFO_FILE")" \
  --title "$PROPOSAL_TITLE" --description "$PROPOSAL_DESCRIPTION" \
  --deposit "$INITIAL_DEPOSIT" --is-expedited=false \
  --from "$PROPOSER_KEY" --home "$PAXD_HOME" \
  --chain-id "$COSMOS_CHAIN_ID" --node "$COMET_RPC_URL" \
  --fees "$FEES" --gas "$GAS_LIMIT" --broadcast-mode block
```

`INITIAL_DEPOSIT` and `FEES` are coin strings containing an amount and
denomination; `GAS_LIMIT` is the selected gas limit. `PROPOSER_KEY` is a local
account alias. Use `--generate-only` to emit an unsigned transaction before
broadcasting. This command takes proposal fields through flags; the example
transaction is not input to `submit-proposal --proposal`, whose JSON schema
contains title, description, type and deposit fields.

Confirm a successful transaction result and take `PROPOSAL_ID` from the
`submit_proposal` event's `proposal_id`. Additional deposits use the proposal
ID and a coin string `ADDITIONAL_DEPOSIT`:

```sh
paxd tx gov deposit "$PROPOSAL_ID" "$ADDITIONAL_DEPOSIT" \
  --from "$DEPOSITOR_KEY" --home "$PAXD_HOME" \
  --chain-id "$COSMOS_CHAIN_ID" --node "$COMET_RPC_URL" \
  --fees "$FEES" --gas "$GAS_LIMIT" --broadcast-mode block

paxd tx gov vote "$PROPOSAL_ID" "$VOTE_OPTION" \
  --from "$VOTER_KEY" --home "$PAXD_HOME" \
  --chain-id "$COSMOS_CHAIN_ID" --node "$COMET_RPC_URL" \
  --fees "$FEES" --gas "$GAS_LIMIT" --broadcast-mode block
```

`DEPOSITOR_KEY` and `VOTER_KEY` are local account aliases. Voting is available
during the proposal's voting period. Set `VOTE_OPTION` to `yes`, `no`,
`no_with_veto` or `abstain`. Confirm each transaction's application result.

## Query proposal and upgrade state

```sh
paxd query gov proposals --node "$COMET_RPC_URL" --output json
paxd query gov proposal "$PROPOSAL_ID" --node "$COMET_RPC_URL" --output json
paxd query gov deposits "$PROPOSAL_ID" --node "$COMET_RPC_URL" --output json
paxd query gov votes "$PROPOSAL_ID" --node "$COMET_RPC_URL" --output json
paxd query gov tally "$PROPOSAL_ID" --node "$COMET_RPC_URL" --output json
paxd query upgrade plan --node "$COMET_RPC_URL" --output json
paxd query upgrade applied v7.0 --node "$COMET_RPC_URL" --output json
```

The proposal query reports its status and deposit and voting deadlines. After
passage, compare the scheduled plan's name, height and decoded `info` with the
submitted values. `upgrade plan` reports an error when no plan is scheduled;
`upgrade applied v7.0` returns the block header at the applied height once the
upgrade has executed.

[upgrade transaction CLI](../../sdk/x/upgrade/client/cli/tx.go),

[governance query CLI](../../sdk/x/gov/client/cli/query.go),
