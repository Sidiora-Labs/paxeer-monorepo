# Paxeer 7.0.0 upgrade plan

This plan covers release `paxeer-network/v7.0.0` of `paxd` and the on-chain plan `v7.0`, which
activates the merged network on Paxeer mainnet-beta (Cosmos chain ID `hyperpax_125-1`, EVM chain
ID `125`, `0x7d`) (docs/runbooks/paxeer-x-fork.md). Read it with the
[validator runbook](7.0.0-validator-runbook.md), the
[service operator runbook](7.0.0-service-operator-runbook.md) and the
[readiness checklist](7.0.0-readiness-checklist.md). The existing
[merged-network validator runbook](../runbooks/paxeer-x-fork.md) stays the reference for the
detailed per-host procedure; this plan schedules and governs it.

Source references identify the implementation behind the activation and operational steps.

## 1. What 7.0.0 brings

7.0.0 makes Paxeer one execution domain: the LayerX kernel runs inside `paxd`, the block
proposer executes transactions in their sequenced order, and a receipt is final when its
block is committed (docs/paxeer-network.md). All fourteen numbered public
endpoints (`api1` through `api14` under `mainnet-beta.paxeer.network`) and the
canonical alias serve JSON-RPC at the node root on chain ID 125, without a
router path (docs/paxeer-network.md). In product terms:

| Area | Change at the upgrade height | Source |
| --- | --- | --- |
| Native ledger | Per-asset ledger balances and transfers at `0x101A` | (node/upgrades.go) |
| Payments | Native payment streams and grants at `0x101B`; streams at `0x0906` | (node/upgrades.go) |
| Authority | Native account authority at `0x101C` | (node/upgrades.go) |
| Programs | Program deployment and calls at `0x101D`, replacing the hosted program routes | (node/upgrades.go, services/platform/hosted/gateway/README.md) |
| Sub-chains | Tenant domains registered by `layerxchains` at `0x101E`, with no new infrastructure | (node/upgrades.go, docs/paxeer-network.md) |
| Agent functions | Order book `0x0901`, clearing `0x0902`, oracle aggregator `0x0903`, proof-of-quality `0x0904`, scheduler `0x0905`, TEE attestor `0x0907`, EIP-712 `0x0908` | (node/upgrades.go, docs/runbooks/paxeer-x-fork.md) |
| Sequenced blocks | From the first block after activation, every block carries a signed sequence batch at position 0 and user transactions in receipt order | (node/upgrades.go, docs/runbooks/paxeer-x-fork.md) |
| Signed receipts | `pax_sequencerReceipt` and `px_getReceiptKeys` report signed execution receipts against governed receipt keys | (rpc/server.go, rpc/sequencer_receipt.go) |
| `px_` methods at the node root | The node serves the `px` namespace beside `eth`, `net`, `pax`, `debug`, `txpool`, `echo` and `test` | (rpc/server.go) |
| Retired surfaces | `layerxVerify` `0x1012` and `layerxCustody` `0x1013` refuse every method; `layerxAnchor` `0x1014` refuses writes and keeps reads until the later deletion plan | (precompiles/common/retire.go, docs/runbooks/paxeer-x-fork.md) |
| Balance effects | Anchor guarantor bonds, pending unbondings and open challenge deposits are returned to their owners; remaining custody balances move to the custody authority and pending custody claims are cancelled | (modules/layerxanchor/keeper/retire_merge.go, modules/layerxcustody/keeper/release.go) |
| Error format | From the upgrade height, refusals of the address-binding `0x1004`, bridge `0x1016` and fee-token `0x1018` precompiles are returned as registry `"<code>: <message>"` reasons | (precompiles/addr/addr.go, precompiles/layerxbridge/layerxbridge.go, precompiles/feetoken/feetoken.go) |

Retained unchanged: the bridge `0x1016`, launchpad `0x1017`, fee token `0x1018`, xweb `0x1019`
and native perps at `0x1015` (docs/runbooks/paxeer-x-fork.md).

### Scheduling

The upgrade is scheduled by height through a governance `software-upgrade` proposal whose
`info` field is the sequencer genesis JSON, not a binaries download document
(docs/runbooks/paxeer-x-fork.md). The handler decodes `leaders`, `receipt_keys`, `last_seq`,
`last_seq_hash` and `activation_height` from `plan.Info` (node/upgrades.go). At height `H`
the running binary stops with `UPGRADE "v7.0" NEEDED at height: H: <info>` and records the plan
in `data/upgrade-info.json` (sdk/x/upgrade/abci.go, sdk/x/upgrade/keeper/keeper.go). The 7.0.0
binary then starts, mounts the new stores because the file height equals the last committed
height plus one, and runs the handler in block `H` (node/app.go, node/upgrades.go).

Governance is the scheduled upgrade path (docs/runbooks/paxeer-x-fork.md). The release tool
generates and validates sequencer genesis with `plan-info` and `plan-info --check`
(tools/release/upgrade_info.py:343–361). For an operator upgrade file, `node --plan-info`
preserves the validated genesis in `info`; `swap.sh --plan-info` forwards it. Merge files
require this input unless the release document already carries it
(tools/release/upgrade_info.py:298–338, tools/release/swap.sh:37).

### Heights

| Symbol | Meaning | Rule | Source |
| --- | --- | --- | --- |
| `H` | Height at which the `v7.0` handler runs | Chosen from measured block time and live governance periods | (docs/runbooks/paxeer-x-fork.md) |
| `S` | First sequenced height | `S = H + 1` when `activation_height` is zero or omitted | (node/upgrades.go) |
| `H_delete` | Height of `v7.0-anchor-store-delete` | Strictly later than `H`, with its own proposal | (docs/runbooks/paxeer-x-fork.md) |

### What the handler does, in order

1. Refuses unless every merge constructor and activation precompile is present (node/upgrades.go).
2. Refuses unless the executing plan is `v7.0` at the current height and equals the scheduled plan (node/upgrades.go).
3. Validates the sequencer genesis: non-empty leader list, `last_seq` zero, a receipt key covering `S` (node/upgrades.go).
4. Runs module migrations with the sequencer taken as present (node/upgrades.go).
5. Retires the anchor module and returns all bonds, emitting `layerx_anchor_retired` with `returned_bond` (modules/layerxanchor/keeper/retire_merge.go, modules/layerxanchor/types/events.go).
6. Initialises the sequencer from the plan genesis (node/upgrades.go).
7. Releases custody: cancels pending claims, sends each custody asset balance to the custody authority, and emits `paxprotocol.paxchain.layerxcustody.EventRetiredRelease` per asset (modules/layerxcustody/keeper/release.go, api/layerxcustody/events.proto).
8. Records the hosted programs guest ABI version and refreshes the kernel program host (node/upgrades.go).

All writes happen in one cached context and are committed only when every step succeeds
(node/upgrades.go). A refusal stops the block that would apply the plan
(docs/runbooks/paxeer-x-fork.md).

### Store changes

| Plan | Added | Deleted | Source |
| --- | --- | --- | --- |
| `v7.0` | `sequencer`, `layerxledger`, `layerxauth`, `layerxpay`, `layerxchains`, `layerxprograms`, `layerxagent`, `lxphost` | none | (node/upgrades.go, storage/common/keys/store_keys.go) |
| `v7.0-anchor-store-delete` | none | `layerxanchor` | (node/app.go) |

The merge store loader adds only stores the database still holds as pending, so a chain that
already carries them is untouched (node/app.go). If a required store is not mounted when the
plan is due, the node stops with a message naming the missing stores (node/upgrades.go).

### Parameter changes

The `v7.0` handler changes no consensus, governance or fee parameters (node/upgrades.go).
Keep the live consensus parameters through the upgrade; a timeout change is a separate
proposal (docs/runbooks/paxeer-x-fork.md). The governance voting periods in force are those the
`v6.10` plan wrote (one hour, twenty minutes expedited) unless governance has changed them
since; read them live (node/upgrades.go).

### Behaviour after activation

- Only validators in the pinned leader list may propose sequenced blocks; a proposal from any
  other proposer is rejected (node/process_proposal_proposer.go).
- The agent scheduler runs due jobs in the end block once the merge is live; its errors are logged
  as `agent end block failed` and do not halt the block (node/legacyabci/end_block.go,
  modules/layerxagent/keeper/scheduler.go).
- Receipt order equals block order: the sequence batch is position 0 and user transactions follow
  in receipt order; JSON-RPC `transactionIndex` stays the EVM-only index
  (docs/runbooks/paxeer-x-fork.md, rpc/tx.go).

## 5. Go / no-go criteria

Go requires every item below; any failure before the cancellation deadline is a no-go and the
plan is cancelled by governance (docs/runbooks/paxeer-x-fork.md).

1. The chain has applied `v6.12.0` and has not applied `v7.0` (`paxd q upgrade applied`) (docs/runbooks/paxeer-x-fork.md).
2. Confirm the running binary's registered plans and halt behavior before scheduling `v7.0` (sdk/x/upgrade/abci.go, node/upgrades.go).
3. The release identity, release check and publish workflows name `v7.0.0` / `v7.0` and passed (RELEASE.md, .github/workflows/paxeer-release-check.yml).
4. `SHA256SUMS` was reproduced independently (RELEASE.md).
5. Candidate release checks passed at one revision: custody release and receipt order are correct, retired surfaces refuse calls, goldens reproduce expected outputs, parity checks show matching execution results, and the retired-caller scan finds no active callers of removed surfaces. Aggregate rehearsal checks also passed. Retain the exact commands, exits and logs ([readiness checklist](7.0.0-readiness-checklist.md#release-checks-and-rehearsal-evidence)).
6. The ordered rehearsal checks pass: `TestMergeRehearsalFirstSequencedBlock`, `TestExportAfterMergeKeepsSequencerState`, `TestMergePlanActivatesGatedPrecompiles` and `TestAnchorStoreDeletedAtStep`. The programme rehearsal runs these steps in order; see the [candidate report](7.0.0-candidate-report.md) for its command (docs/runbooks/paxeer-x-fork.md).
7. The passed proposal's name, height and decoded `info` equal the reviewed plan; at least one receipt key covers `H+1` (node/upgrades.go).
8. Every pinned leader is an active validator whose operator confirmed sequencing configuration and receipt key staging (node/process_proposal_proposer.go, node/sequencer/config.go).
9. Validators with more than two thirds of voting power, plus margin, confirmed staging and availability (docs/runbooks/paxeer-x-fork.md).
10. Consistent stopped-node backups are possible on every validator: disk headroom checked, all PaxDB directories inventoried (docs/runbooks/paxeer-x-fork.md).
11. The hosted gateway, explorer and agent daemon have their receipt-key material prepared from the passed plan (services/platform/hosted/gateway/README.md, services/explorer/backend/config/runtime.exs).

**Source of truth:** The [merge specification](../../spec/layerx-merge/spec.kvx)
defines the release acceptance criteria. The candidate report must show what each
check proved and retain its revision, command, exit status and evidence location.

## 6. Halt and rollback criteria

The default response to a failure after `H` is to keep affected nodes stopped, preserve logs,
databases, WAL and signing state, and ship a repair release; restarting the old binary against
migrated stores, `--unsafe-skip-upgrades` and signing-state resets are prohibited
(docs/runbooks/paxeer-x-fork.md). Same-chain snapshot restore is refused by the release tooling;
forward recovery with a repair binary is the supported path (RELEASE.md, tools/release/rollback.sh).

| Trigger | Decision |
| --- | --- |
| Handler refusal at `H` (`carries no leader list`, `want 0`, `pins no receipt key for first sequenced height`, `sequencer genesis`, `missing merge constructors or activation precompiles`, `executing plan differs from scheduled plan`) | Network stays halted at `H`. A refusal means the plan info or binary is wrong. Recovery is a coordinated repair binary or a new plan agreed by governance once the chain can produce blocks; never a local skip (node/upgrades.go, docs/runbooks/paxeer-x-fork.md) |
| Startup panic naming missing stores | The upgrade file height did not equal last committed height plus one; correct the restart sequence, do not edit the plan (node/upgrades.go) |
| No block at `S` within the agreed window | Check that pinned leaders are online and proposing; non-leader proposals are rejected by design (node/process_proposal_proposer.go) |
| App hash divergence between validators after `H` | Halt affected validators, compare binary hashes and native library digests, coordinate a repair binary (tools/release/build-paxd.sh) |
| Balance effects differ from rehearsal (bond return total, custody release amounts) | Halt new admissions at services, record evidence; a source revert does not undo committed payouts (docs/runbooks/paxeer-x-fork.md) |
| Retired precompile answers success after `H` | Treat as a consensus defect; halt service cutover and ship a repair (precompiles/common/retire.go) |
| Before `H`, any go criterion fails | Cancel with `cancel-software-upgrade` while it can still pass (docs/runbooks/paxeer-x-fork.md) |
