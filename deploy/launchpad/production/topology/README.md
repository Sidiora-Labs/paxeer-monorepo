# Topology v1: provisional production declarations

This directory supplies the offline [topology compiler](topology.py), its validation contracts and a [connected operator](phase2/operator-runbook.md). A rendered plan establishes configuration arithmetic and resource declarations; it does not establish deployment, throughput or safe failover. The 500,000 daily-active-user target and the zone-loss, failover, transport, database and capacity scenarios require signed measurements for the exact candidate.

The application consumes one Paxeer network: `paxd` runs the BFT chain, the kernel participates in the network and proposes blocks, and EVM chain ID is 125 (`0x7d`). A transaction receipt is final when its block is committed. Public JSON-RPC uses HTTPS at the root path of `api1.mainnet-beta.paxeer.network` through `api14.mainnet-beta.paxeer.network`, plus `api-mainnet-beta.paxeer.network`. Choose two to eight distinct, verified node URLs for `rpcEndpoints`; for example, `https://api1.mainnet-beta.paxeer.network/` and `https://api2.mainnet-beta.paxeer.network/`. `node.hyperpaxeer.com` is only the hpx library mirror, never an RPC endpoint. Sub-chains are tenant domains in the database and do not require a new infrastructure fleet.

`production-input.template.json` deliberately fails validation. Fill every null using reviewed provider inputs and measured resource budgets. `fixtures/synthetic-config.json` contains explicitly synthetic, unpullable `example.invalid` images, provider names and test-only digests. It is only an offline validator fixture. Its 4 TiB PostgreSQL allocation illustrates expansion beyond the provisional 2 TiB; it is not an approved purchasing recommendation or measured production allocation. Derived streams and overhead values in that fixture are test assumptions.

Commands, from the monorepo root containing `deploy/launchpad/production` and `tools/launchpad/production` (not from this directory). Keep that root as `--source-root` when following the connected operator runbook:

```sh
python3 deploy/launchpad/production/topology/topology.py validate --config /reviewed/topology.json
python3 deploy/launchpad/production/topology/topology.py render --config /reviewed/topology.json --output /reviewed/plan.json
python3 deploy/launchpad/production/topology/topology.py verify-plan --config /reviewed/topology.json --plan /reviewed/plan.json
python3 deploy/launchpad/production/topology/topology.py check-evidence --config /reviewed/topology.json --plan /reviewed/plan.json --evidence /reviewed/measured.json
```

Offline development checks, with their dependencies installed:

```sh
python3 -m unittest discover -s deploy/launchpad/production/topology/tests -v
python3 deploy/launchpad/production/topology/native_nats_check.py
```

The JSON `plan.resources` is a Kubernetes List; extract it into a separately reviewed manifest for API server dry-run. The compiler never invokes kubectl, fetches secrets, modifies a cluster, signs evidence or promotes a release. API server dry-run, CNI enforcement, CNPG admission/controller operation and pinned application image startup must occur in an isolated qualification environment before any deployment. The pinned official CNPG 1.29.0 Cluster/Pooler CRD snapshots support offline schema checks only; provenance URLs and byte hashes are in `fixtures/crd-provenance.json`. Python tests require installed PyYAML and jsonschema; native NATS parsing requires Docker, OpenSSL and the preinstalled pinned bootstrap broker image. The parser refuses implicit image pulls, uses no network, creates temporary test TLS material, requires the broker's actual configuration-validity marker and removes its uniquely named container.

## Contracts and arithmetic

The compiler accepts closed topology schemas 1 and 2: unknown or missing object fields fail, integer types reject booleans/floats, strings and arrays are bounded, duplicate JSON keys fail, images require full SHA-256 references, RPC URLs require HTTPS without user information, queries or fragments, and three distinct provider zone names are required. Version 1 declares seven application roles; version 2 adds explicit `workloads` and `runtimeDocuments` for all twelve roles in `RUNTIME_ROLES` and is required by the connected operator. Zone names do not prove independent failure domains; the signed measured inventory must establish that. Secret references are names only. Each service gets a distinct runtime Secret reference, distinct from the database bootstrap owner, broker server authentication and TLS references. No production credentials belong in topology files.

The normal workload is 1,000,000 sessions/day, 900 seconds each, 50 dynamic requests/session: 50,000,000 requests/day and exact average concurrency 31,250/3 (10,416.67 rounded). Peak and burst targets are separate: 10,000/20,000 dynamic RPS, 100,000/200,000 connected clients; 2,000 write and quote RPS are subsets. Version 1 starts API at 24 replicas and sockets at 30; zone-loss survivors require 625 RPS/API and 5,000 connections/socket replica. Burst targets require 48 API and 60 socket replicas provisioned before exposure, or separately qualified equivalents. Version 2 takes allocations from `workloads`; the arithmetic targets do not prove those allocations can serve the load. CPU HPA is a starting guard, not a socket/latency/autoscaler capacity proof. D16 must test actual metrics-based scaling and pre-surge provisioning.

At 1,200 bytes/raw event, normal 72h retention is 36,000,000,000 logical / 108,000,000,000 R3 bytes. A separate 2,000/s, 72h qualification budget is 622,080,000,000 logical / 1,866,240,000,000 R3 / 3,732,480,000,000 raw-only bytes with twofold headroom. One 24h peak day is 207,360,000,000 raw bytes. Each derived stream is separately itemized, replicated three times, charged broker overhead, rounded up per stream and given twofold headroom. The sum of rendered per-stream `max_bytes` times R3 must fit the actual NATS configured `max_file_store` limit: 90% of each PVC. It must not compare against the larger unallocatable full volume. The remainder covers filesystem space; actual required free-space policy must be confirmed by measurement.

The raw and derived stream contracts use file storage, R3, 72h `max_age`, discard-new and deny-delete/purge. The contracts are delivered in `jetstream-stream-contracts`; a separate authorized reconciler must apply them, reject drift and verify actual replica zone placement. Merely creating three broker processes does not create any stream. Durable consumer inbox/outbox acknowledgement and deduplication remain L08 integration obligations; JetStream duplicate-window settings do not replace them. The built-in `raw-chain` stream name is reserved.

PostgreSQL's 30-day fixture includes 29 normal days and one full peak day: 555,360,000,000 raw bytes, 1,666,080,000,000 row/index-amplified bytes per member, 4,998,240,000,000 across three copies. Required per-member capacity adds explicit derived tables, WAL and vacuum workspace and reserves the configured 20–50% free headroom. This validator rejects the synthetic fixture at the provisional 2 TiB. Replication copies are not extra usable space for a single writer's database.

Maximum server connections are 600, with 60 reserved. Three transaction poolers have separate bounded per-database and per-user caps; `3 * serverConnectionsPerPooler + otherDirectConnections` must be at most 540 for schema 1 and 480 for schema 2. These declaration limits remain separate from the measured connection checks. This assumes exactly the declared application database; add database/user/pool partitions to the global budget before enabling them. The version-1 maximum API allocation of 48×8 gives 384 potential client connections, not 384 permanent PostgreSQL server slots. Pool acquisition is bounded at ≤1s. CNPG quorum-based synchronous replication with required durability and failover quorum declares the intended writer safety; independent controller-version fencing proof is mandatory. Do not relax synchronous settings to hide unavailable capacity.

Steady market payload is 100 MB/s (0.8 Gbit/s); burst is 400 MB/s (3.2 Gbit/s), before measured TLS/framing overhead. Media 20,000×2 Mbit/s is 40 Gbit/s through the managed CDN, with zero API media payload. No bytes/sec claim here is a benchmark.

## Runtime and provider prerequisites

Service images must implement `/health/live` as process-only, `/health/ready` with explicit dependency reasons, and a separate mutation-ready decision. PostgreSQL loss must fail writes without restarting healthy processes; stale read responses require snapshot age and quality, never a fake current value. SIGTERM must first remove readiness, allow five seconds propagation, then drain for at most 30 seconds inside 45 seconds orchestrator grace. Stop admission before draining, retain completed write receipts, fail uncompleted work retriably and reconnect sockets using durable replay cursors. The declarations pass these requirements as configuration; existing service mains are not presumed to implement them.

Indexer leadership must use the durable fenced lease. Verify `eth_chainId` is `0x7d` and compare accepted committed hashes across verified RPC endpoints; an inconsistent endpoint must be quarantined and raise an integrity incident. The compiler declares `CHAIN_ID=125`, `COMMITTED_FINALITY=true`, `CONFIRMATION_WAIT_BLOCKS=0` and `RPC_CONFLICT_POLICY=quarantine_endpoint_no_rollback`; these settings require corresponding runtime behavior. Never implement ordinary rollback or confirmation delay on Paxeer committed blocks. Redis shards are expendable caches, using a consistent partition strategy. Loss cannot remove accepted business events; sensitive admission fails closed where distributed rate-limit authority is unavailable. PostgreSQL cold reads and socket queues remain bounded. The default-deny network policy intentionally blocks external RPC/CDN egress until L45 approves exact gateways/CIDRs and TLS/DNS controls; no open Internet egress is synthesized.

CNPG operator control-plane, Kubernetes API and exporter access policies are external prerequisites. CNPG-generated database/bootstrap/pooler identities, storage-class encryption, independently provisioned per-zone volumes, actual image pull secrets, runtime secret key compatibility and TLS renewal must be reconciled before API dry-run/activation. Redis secret `redis.conf` must declare TLS-only authenticated access, disabled persistence and bounded eviction; the parser does not assert contents of an absent secret. NATS `accounts.conf` must grant each service its own NKey/account permissions and prohibit wildcard administrative rights; server mTLS and authenticated route TLS are declared. Data-plane broker/database Services are ClusterIP only. Version 1 exposes API/socket ingress; version 2 additionally routes to `gateway`, `user`, `metadata` and `livestream` as declared in `compile_plan`. These are application routes, distinct from the public node JSON-RPC. DNS egress is limited to the cluster DNS namespace/pod identity. Provider enforcement and controller-created resources must also be audited.

## Evidence, promotion and lifecycle

`validate_evidence` requires all eighteen named scenario records, UTC intervals, deployment/config/source/interface identities, input/reconciliation/inventory/artifact digests and named metric sample counts. It checks reported throughput, zero acknowledged-write loss, zero duplicate database effects, one writer, ingest ≤500ms, drain ≤30s, bounded probes/recovery and per-derived-stream/PG/broker budgets. Claimed soak duration cannot exceed the evidence interval. Missing, expired, mismatched, failed or incomplete records are rejected. This offline check validates declarations about measurements; it does not open the referenced artifacts or authenticate their origin. External signed attestations must bind the complete evidence bytes and resource inventory to a trusted CI/operator identity; a 64-character digest is not authentication. The connected operator verifies signatures and artifact bytes. The offline result always says `notDeploymentAuthorization: true` and cannot promote anything.

The [connected operator](phase2/operator-runbook.md) implements durable control transitions in a SQLite journal: `proposed` → `validated` after exact plan + API admission + signed qualification, then `validated` → `activated` for the same revision/digests after trusted actor authorization. Explicit rejection requires signed authority; evidence or dry-run failures after validation authenticates the actor reject the proposal. Audit records and durable activation intent bind the actor and candidate. Monotonic proposal revisions and compare-and-swap against the active revision prevent stale activation; rejected proposals remain in the journal. Stale evidence must stop before the first replica changes. The external canary controller must provide measurements at 5% for ≥600s with passing SLO/accounting invariants. The operator verifies that evidence before activation and does not implement staged traffic routing. Rollback is a separately authorized digest-pinned revision compatible with database/schema and durable epochs, never implicit database downgrade.

The offline compiler does not implement these control transitions. The connected operator adds signed evidence checks, Kubernetes operations and journal recovery, subject to the source prerequisite documented in its [runbook](phase2/operator-runbook.md#source-and-runtime-prerequisites). Measured canary traffic routing, shared environment registration and production-shaped application scenarios remain external responsibilities.

Phase 3 adds interpreted adversarial outcomes, exact receipt/effect reconciliation and incident timelines to the connected operator. The [operator runbook](phase2/operator-runbook.md#phase-3-adversarial-evidence-and-isolated-rehearsal) specifies the additive signed evidence and isolated rehearsal interfaces. Provider snapshots remain distinct from measured application qualification.

The Phase 4 `phase2.capacity` CLI captures actual topology allocations and authenticated native telemetry, then evaluates source-bound D16 shared captures and Phase 3 reconciliation. Its machine-readable results preserve the final shared `9.1` release boundary. See the [capacity capture instructions](phase2/operator-runbook.md#phase-4-native-capacity-capture).
