# Issue 1652: [P2] Return valid BufferedTask retry entries from multichain export fetchers

## Impact

Both multichain export fetchers return a map in the list-valued `BufferedTask` retry slot. An ordinary failed upstream export performed by the running queue worker therefore crashes that worker while handling its result, instead of scheduling a valid retry.

This consumer mismatch predates [08da21d2377053a40a0d0eb5793d404b4bcac9c6](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/08da21d2377053a40a0d0eb5793d404b4bcac9c6), but remains after that commit's malformed-200/mixed-error recovery repair. Verified by static inspection on current main `44823b0a8346dd793d93d2e438a7b4688d933eda`.

The durable rows remain available for restart. This report concerns worker/retry instability and missing failure-path integration coverage; it does not claim data loss or a measured deployed outage.

## Producer / consumer trace

1. [MultichainSearch.batch_import/1](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/explorer/lib/explorer/microservice_interfaces/multichain_search.ex#L66-L90) returns `{:error, data_to_retry}`, where the payload is a flat map of addresses, hashes, ranges and balances. [Malformed HTTP 200 JSON](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/explorer/lib/explorer/microservice_interfaces/multichain_search.ex#L940-L953) now correctly enters this typed failure path.
2. [MainExportQueue](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/fetcher/multichain_search_db/main_export_queue.ex#L91-L112) returns `{:retry, data_to_retry}`; [BalancesExportQueue](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/fetcher/multichain_search_db/balances_export_queue.ex#L83-L88) returns the same map shape.
3. [BufferedTask.handle_info/2](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/buffered_task.ex#L741-L743) forwards the value to [drop_task_and_retry/3](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/buffered_task.ex#L931-L937), then [push_back/2](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/buffered_task.ex#L1081-L1082).
4. [push/3 only has a list-guarded clause](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/buffered_task.ex#L1121-L1122). Passing the map produces a FunctionClauseError in the BufferedTask process.

Simply wrapping the map in a list is insufficient: the fetchers' list paths expect persisted queue entries. MainExportQueue's [prepare_export_data/1](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/fetcher/multichain_search_db/main_export_queue.ex#L180-L223) reads each entry's `hash_type`, while BalancesExportQueue's [prepare_export_data/1](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/lib/indexer/fetcher/multichain_search_db/balances_export_queue.ex#L158-L185) reads `token_contract_address_hash_or_native`. The wire-format retry map has neither row shape.

## Why current recovery tests miss it

The new [malformed-success test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/explorer/test/repair/repair_22_33_455_test.exs#L257-L282) calls `MainExporter.run/2` directly and asserts the returned map. Its restart helper first runs with dispatch disabled, then [switches the upstream to HTTP 200 before enabling dispatch](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/explorer/test/repair/repair_22_33_455_test.exs#L333-L354). No failing result is delivered to BufferedTask.handle_info/2.

The earlier task 22.33.557 helper in [export_queue_contract.exs](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/44823b0a8346dd793d93d2e438a7b4688d933eda/services/explorer/backend/apps/indexer/test/indexer/fetcher/multichain_search_db/export_queue_contract.exs#L70-L99) uses the same direct-failure/successful-reopen pattern.

## Expected versus actual

Expected: a failed export from a running fetcher keeps valid retry work, preserves durable rows, and can succeed later without crashing the queue worker because of the callback result shape.

Actual: both fetchers return a wire-format map where BufferedTask requires a list of callback entries, causing the worker's result handler to raise.

## Reproduction / validation

In a disposable configured explorer/indexer test database:

1. Insert at least one valid MainExportQueue row and enable its actual fetcher supervisor with nonzero concurrency.
2. Use a local HTTP listener that returns 503, or HTTP 200 with malformed JSON, for `/api/v1/import:batch`.
3. Let BufferedTask dispatch the row and consume the fetcher's result. Monitor the worker PID/logs for the result-handler FunctionClauseError.
4. Repeat with a valid BalancesExportQueue row.
5. After the fix, make the listener return success and assert the original work is exported and the corresponding durable queue drains.

This is a source-derived reproduction plan, not an executed test result.

## Acceptance criteria

- Both fetchers produce scheduler-compatible retry results containing valid callback entries, or use an explicitly supported rescan/retry mechanism.
- Test failures through the real running BufferedTask supervisor, not only direct `run/2` calls.
- Cover 503 and malformed-200 responses, followed by success, for both main and balance queues.
- Assert the queue worker survives failure handling, failed durable work remains recoverable, and successful replay drains the appropriate rows.
- Preserve partial-success behavior and existing request/persistence assertions.
