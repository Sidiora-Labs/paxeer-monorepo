# Issue 1850: [P2] Provide Docker for Autobahn before routing it to the Fly runner

## Summary

e0a5a9cb96428465da9d597a1a0df041a92fca04 changes Autobahn integration from hosted Ubuntu to the configurable routed runner. The checked-in Fly runner lacks Docker, but the job starts a Docker cluster through Make and Go TestMain without provisioning a runtime. The routing checker misses that indirect dependency.

Reviewed source: 2c237932ad29a58cd69eabd8f7a97a9a29bf28b1. This is a CI prerequisite regression, not an observed deployed consensus failure.

## Expected versus actual and impact

Expected: the supported configured CI runner can start the disposable Autobahn cluster and reach the integration assertions, or this Docker-dependent job stays on a compatible hosted runner.

Actual from source: with the checked-in Dockerless Fly image selected, the invoked Make targets cannot execute Docker, setupCluster returns an error, and TestMain exits before m.Run. This prevents the Autobahn integration regression suite from testing block production, transfers, fault tolerance, and recovery. It does not demonstrate a production consensus fault. Live CI_LINUX_RUNNER values and deployed-image customizations were not inspected.

## Acceptance

- Keep Autobahn on a Docker-capable hosted runner with a justified exclusion, or explicitly provision and prove the runtime before this Make target. Preserve fork safety.
- Reconcile the restored-job assertion with that actual capability requirement.
- Add focused coverage for the real Make/Go cluster dependency, including a Dockerless-runner negative, rather than only recognizing direct Docker text.
- In an authorized disposable CI environment, confirm the job reaches m.Run and its existing assertions without weakening them.
