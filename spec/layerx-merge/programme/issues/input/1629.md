# Issue 1629: [P2] Restore retention eligibility for reappearing archived snapshots

## Summary

An acknowledged snapshot that has been retired from the active replica ledger and later reappears with identical bytes is recognized by the shipper, but never becomes eligible for the production backup writer's retention deletion again.

Introduced by [63cb3830 (repair 22.33.148)](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/63cb383086ee54b00ac957e9819834b407a3215b). Reverified on current main `7e7f8b9163d781d3ac5b5e19700f5e0b97ac4c81`.

## Expected versus actual

Expected: with replica shipping configured, an older local snapshot with a valid matching acknowledgment should remain eligible for retention deletion, including when its acknowledgment was archived while the file was absent. Unshipped snapshots and snapshots with changed bytes must remain protected.

Actual: the shipper validates the archived acknowledgment and skips uploading, but leaves the entry absent from the active ledger. The writer sees no acknowledgment through its active-only Lookup interface and silently keeps the old file on every retention pass.

## Concrete validation steps

Use an integration fixture with the real backup.Writer, replica ledger/shipper, and test SFTP server. Use the writer's valid node-specific snapshot names rather than the arbitrary .bin names in the replica-only test.

1. Configure Retain=1 and Shipped=shipper.Ledger().
2. Create snapshot A, save an exact copy of its bytes, and successfully ship it.
3. Create newer snapshot B and successfully ship it. Run Writer.Retain if necessary so A has been deleted while B remains.
4. Run Ship again to archive A's acknowledgment after its local file is absent.
5. Restore the saved identical bytes under A's original path.
6. Run Ship: the archived acknowledgment matches, no re-upload is needed, and A is not put back into the active ledger.
7. Run Writer.Retain.

Expected: A is deleted, B remains. Source-derived actual: A is silently skipped because Lookup(A) is false. Repeated Ship/Retain passes and reopening the ledger preserve that condition.

## Impact and test gap

Conditional local storage retention failure after archived snapshots reappear, for example after restoring an older snapshot-directory copy. Extra retained storage is proportional to the reintroduced acknowledged files; this does not claim that ordinary uninterrupted operation grows without bound.

The [new long-history/reappearance test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/7e7f8b9163d781d3ac5b5e19700f5e0b97ac4c81/services/wallet/attestor/internal/replica/repair_m148_test.go#L24-L150) tests duplicate shipping and changed-byte refusal, but manually deletes local files instead of exercising the real writer's retention consumer.

## Acceptance criteria

- Matching archived acknowledgments can support retention of reappearing local snapshots, either by safely reactivating them or through a consistent acknowledgment lookup contract.
- An integration regression using the real Writer.Retain reproduces the sequence above and verifies removal of A while B is retained.
- Cover reopening/restart, repeated Ship/Retain, and unchanged duplicate shipping behavior.
- Preserve digest/size validation and refusal/protection for changed bytes and unshipped snapshots.
- Preserve the bounded active-ledger objective.
