# Issue 1659: Replay held-job diagnostic bypasses retry handling during database outages

## Problem
At [42be9d9d](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/42be9d9d164f49898372ab3aa2932cc0a735223e), [PriceAcceptanceReplay](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/42be9d9d164f49898372ab3aa2932cc0a735223e/services/explorer/backend/apps/indexer/lib/indexer/fetcher/paxeer_x/price_acceptance_replay.ex#L33-L66) calls `held_jobs()` after each replay step before scheduling the next retry. The diagnostic uses [Repo.query!](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/42be9d9d164f49898372ab3aa2932cc0a735223e/services/explorer/backend/apps/explorer/priv/repo/migrations/scripts/price_acceptance_backfill.exs#L25-L35), so a database error raises. In contrast, [the replay step rescues database failures into a retryable result](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/42be9d9d164f49898372ab3aa2932cc0a735223e/services/explorer/backend/apps/explorer/priv/repo/migrations/scripts/price_acceptance_backfill.exs#L64-L70). The diagnostic was added in [bbfe819c](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/bbfe819c82aa62bccf0821cf2232131f78821327).

## Expected versus actual
A temporary database failure should leave the replay worker alive and retry on the scheduled interval; diagnostics should not override that recovery. Instead the unhandled diagnostic exception can crash the transient worker before it schedules the retry. [Startup immediately queues replay](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/42be9d9d164f49898372ab3aa2932cc0a735223e/services/explorer/backend/apps/indexer/lib/indexer/fetcher/paxeer_x/price_acceptance_replay.ex#L6-L29), so repeated outages can produce rapid restarts under the [shared supervisor](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/42be9d9d164f49898372ab3aa2932cc0a735223e/services/explorer/backend/apps/indexer/lib/indexer/fetcher/paxeer_x/price_updates_supervisor.ex#L24-L33).

## Validation
Inject a temporary database query failure while the runner handles a replay message. Observe that `step` returns an error but `held_jobs()` raises before the timer is set. Restore the database and verify recovery. A regression test should assert the worker remains alive, the retry is scheduled and replay resumes after recovery, including the initial nil-warning-timestamp case.

## Acceptance criteria
- Make held-job diagnostics non-fatal when the database is unavailable, preserving the normal bounded retry path.
- Test initial startup and subsequent outages, worker stability and successful recovery.
- Preserve useful held-job warnings when the diagnostic query succeeds.

Static source inspection only; no outage or recovery test was executed. This is distinct from closed #922, which covers a different buffered-task retry path.
