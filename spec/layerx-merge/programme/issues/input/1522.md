# Issue 1522: [Coherence] The dashboard's next floor is checked against a new standalone lockfile that the dashboard build never uses, so the shipped dashboard still resolves next 16.3.5

## Defect and impact

The developer dashboard has no install of its own. Both `make developer-dashboard-install` and the Docker image symlink its node_modules to apps/web/node_modules and install from apps/web/package-lock.json, and a lock-consistency script requires every dashboard pin to match that lock exactly. This commit raises the dashboard pin to next 16.4.1 and adds a separate services/platform/hosted/dashboard/web/package-lock.json. lockfloor.py picks that new lockfile as the nearest one, so the dashboard floor passes while the build still resolves next 16.3.5 from apps/web. The pin and the lock the build uses now disagree, and scripts/ci/developer-dashboard-lock.mjs gains a new next mismatch (it already fails earlier on the @layerx/ui path). Task 22.24.15, still pending, raises apps/web to 16.4.1, but even after that lands the floor gate will keep reading a lockfile no build uses.

Kind: cross-system. Severity: major.

## Expected versus actual

Expected: The dashboard's next floor is checked against apps/web/package-lock.json, the lock the dashboard actually installs from, and the pin stays equal to that lock as developer-dashboard-lock.mjs requires. No standalone dashboard lockfile is added.

Actual: A new, unused dashboard package-lock.json makes the floor pass at 16.4.1, while the built and shipped dashboard still runs next 16.3.5 from apps/web and the dashboard pin no longer matches the lock it builds from.
