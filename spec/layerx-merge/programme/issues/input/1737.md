# Issue 1737: [Coherence] Task 22.31.559 and decision 2632 say restart recovery keeps an EvidenceVersion refusal for legacy-archive records, but main has no such refusal, and the one change that would add it is now scheduled after 22.31.559

## Defect and impact

The new decision and the do_1 step of 22.31.559 say a record under the legacy archive key 'keeps the EvidenceVersion refusal'. On main, serve_kernel_evidence checks the legacy key first and returns that version 1 record as evidence, so evidence_inventory lists it under with_evidence and refuses nothing. That refusal exists only in the unlanded attempt tree of 22.33.1537, and this commit makes 22.33.1537 depend on 22.31.559, so 22.31.559 is built and qualified without it while both tasks change evidence_inventory in receipt.rs. A receipt migrated through migrate_authenticated_evidence keeps its version 1 bytes under the legacy key and its current record under the public key, and the spec never says which one recovery should use; if the planned refusal is applied as written, the whole tenant inventory fails for every migrated receipt instead of using its verified current record.

Kind: cross-system. Severity: major.

## Expected versus actual

Expected: 22.31.559 should describe main as it is: legacy-archive records are currently admitted as version 1 evidence. It should either own the refusal or leave it to 22.33.1537, and it should say whether a migrated receipt that has both records recovers from its current record.

Actual: The spec describes a refusal that main does not have as existing behaviour, assigns the receipt.rs inventory change to two tasks in conflicting order, and leaves migrated receipts with no defined outcome, which could fail the whole tenant inventory.
