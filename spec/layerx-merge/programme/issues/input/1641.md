# Issue 1641: [P3] Rebind transfer metric instruments when repeating MetricContract

## Defect and impact

The new transfer metric contract test cannot collect the keeper's instruments on a second invocation in the same test process. It creates and installs a fresh OpenTelemetry provider each time, but the keeper's package-level instruments remain bound to the first provider, which the first invocation shuts down.

This is a test-repeatability/isolation defect. No production transfer, balance, or custody impact is claimed.

## Provenance and source proof

Introduced by [044c26f529733b3073e685c1d3e4ed16a014e9e4](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/044c26f529733b3073e685c1d3e4ed16a014e9e4), task 22.33.1205. Rechecked unchanged on main at bc89ac92e6b057c652ed13ec42725107008ccbf9.

1. [TestRepairM_1205_MetricContract creates a provider, installs it globally, and shuts it down in cleanup](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/interchain/modules/apps/transfer/keeper/repair_m1205_test.go#L152-L156).
2. [The keeper meter and all four instruments are created once at package initialization](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/interchain/modules/apps/transfer/keeper/metrics.go#L8-L37). The test does not recreate or rebind them.
3. The repository pins [OpenTelemetry v1.45.0](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/go.mod#L94). Its [SetMeterProvider implementation delegates previously created instruments only once](https://github.com/open-telemetry/opentelemetry-go/blob/v1.45.0/internal/global/state.go#L119-L138), through sync.Once. [Meter delegation likewise documents and implements this one-time binding](https://github.com/open-telemetry/opentelemetry-go/blob/v1.45.0/internal/global/meter.go#L27-L48).
4. The test [collects from its newly created reader](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/interchain/modules/apps/transfer/keeper/repair_m1205_test.go#L215-L223), then [requires all four keeper instrument names](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/interchain/modules/apps/transfer/keeper/repair_m1205_test.go#L270). On a second invocation that reader owns none of the existing keeper instruments.

## Expected versus actual

Expected: each invocation observes its own real transfer callbacks, including when Go repeats the test within one binary.

Actual, by source inspection: the second invocation's calls still target the first provider's instruments, while its new reader collects no keeper metrics. The final instrument-set assertion therefore cannot match.

## Reproduction / validation

Static review only. No build or test command was executed, and no runtime failure output is being claimed. In the repository's configured Go build environment, run:

```sh
go test ./interchain/modules/apps/transfer/keeper -run '^TestRepairM_1205_MetricContract$' -count=2 -v
```

The second invocation should expose the empty instrument set at the final assertion, assuming prerequisite build/setup succeeds.

## Repair scope and acceptance criteria

Suggested owner: transfer keeper / domain 6, task 22.33.1205.

- Bind the actual keeper instruments to the test's provider for each invocation, or isolate the test's telemetry lifecycle without relying on the one-time global delegation.
- Restore any replaced global/instrument state during cleanup.
- The focused command above passes both invocations.
- Keep the real packet producer path and existing metric name, type, unit, label, amount, and branch assertions intact. Do not weaken or skip the assertions to accommodate an empty reader.
