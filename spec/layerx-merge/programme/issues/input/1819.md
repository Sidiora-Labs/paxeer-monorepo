# Issue 1819: [P2] Reject stale source bindings in the layout receipt prerequisite

## Problem
The new fleet prerequisite gate accepts a retained layout PASS receipt after relevant checkout contents change, as long as repository-layout.json is unchanged. It validates the receipt's schema/status and mapping generation, but does not compare its recorded source bindings with the current source being qualified.

This is a conditional source-supported qualification defect in the developer tooling, introduced by 34c8243fbb04238f2e9ca95cbb94ea32029c5b70. No runtime test, deployed effect or production authorization bypass is claimed.

## Contract and source evidence
- [Requirement 15.7](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/spec/hyperfide-source-control/spec.kvx#L191-L201) explicitly requires a **current** layout qualification receipt before fleet task 0.10. [Task 0.9](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/spec/hyperfide-source-control/spec.kvx#L353-L366) binds actual final-source qualification and refuses stale mandatory evidence.
- [The producer captures source revision, subtree tree and working-source snapshot](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/tests/hyperfide/cases/source_control/0_9.py#L45-L69), not just the mapping digest.
- [require_layout_receipt](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/tests/hyperfide/cases/source_control/0_10.py#L234-L253) only compares mapping_sha256 and layout_generation with the current checkout after validating schema/PASS. It never compares the retained source snapshot/tree or repeats scoped tracked cleanliness checks.
- [0_10.main](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/tests/hyperfide/cases/source_control/0_10.py#L254-L277) then runs fleet parser/index fixtures and independently stamps their current source revision. It does not establish current layout qualification.

## Concrete regression case to add
1. Obtain a genuine PASS receipt from 0_9 for checkout A and retain build/layout/0.9/receipt.json.
2. Introduce a tracked obsolete services/ container under the Hyperfide root, or a relevant root-workspace membership change, without modifying repository-layout.json.
3. Run the direct task-0.10 verifier. Its receipt prerequisite still accepts A's PASS because the only compared current fields are unchanged. Fleet parser/index fixtures need not notice the unrelated layout change.
4. A fresh [0_9 layout check](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/tests/hyperfide/cases/source_control/0_9.py#L594-L600) rejects the obsolete container, demonstrating the difference between historical PASS and current qualification.

This case is source-derived and was not executed. The independently invoked [pending-aggregation checker](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/tests/hyperfide/cases/source_control/layout_pending_aggregation_check.py#L41-L57) reruns 0_9 and would detect this change. However, the [direct 0.10 verify_cmd](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/tools/hyperfide/spec/hyperfide-source-control/spec.kvx#L368-L382) runs 0_10.py alone and does not invoke that checker.

## Expected correction
Validate the receipt against the current relevant source snapshot/subtree and scoped cleanliness policy before accepting it, or require a fresh producer result. Preserve intentional tolerance for unrelated changes outside the Hyperfide root; comparing whole-host HEAD alone would reintroduce the unrelated-root-change problem.

Add stale-source tests using a genuine valid receipt, alongside existing stale-mapping/generation tests.

## Ownership and verification
Task 0.9 remains in_progress with owner repository-layout; task 0.10 is implemented/ahead with owner fleet-prerequisite. This reports a concrete gap in the landed consumer for those owners, not a claim that pending runtime qualification is complete.
