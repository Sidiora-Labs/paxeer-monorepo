# Issue 1818: [P2] Supply the required dashboard API origin during the Docker build

## Problem
The new required DASHBOARD_API_ORIGIN setting is checked while Next loads its production build configuration, but the canonical dashboard Docker build does not supply that setting. Once the preceding install/static stages pass, `npm run build` reaches the new throw instead of producing the standalone image.

This is a source-supported build/configuration regression introduced by 60915c06e54c5c6abeecd2387d033f8732266117. No image build or deployed outage was reproduced.

## Source evidence
- [next.config.ts lines 5–11](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/services/platform/hosted/dashboard/web/next.config.ts#L5-L11) only permits the loopback fallback outside production and throws when the production origin is missing.
- [The Docker build stage](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/docker/platform-dashboard-web/Dockerfile#L1-L12) copies the dashboard and runs `npm run build` without an ARG, ENV or other input for DASHBOARD_API_ORIGIN. The copied tracked dashboard directory has no .env file supplying it.
- [The dashboard build script](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/services/platform/hosted/dashboard/web/package.json#L5-L10) runs `next build`. The shared installed lock pins Next 16.4.1.
- In [the pinned Next 16.4.1 CLI](https://github.com/vercel/next.js/blob/7217011ac0d689026884dd28536a0c7f3c98ba77/packages/next/src/bin/next.ts#L85-L113), non-dev commands default NODE_ENV to production before the command runs. [The build then loads the production config](https://github.com/vercel/next.js/blob/7217011ac0d689026884dd28536a0c7f3c98ba77/packages/next/src/build/index.ts#L1188-L1195).
- [The configured rewrite destination](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/97835484dd9f3503c0cfd6d55bc5b2f0a4536014/services/platform/hosted/dashboard/web/next.config.ts#L21-L27) also uses this value at build time. Merely adding a runtime container environment variable will not repair a failed build or replace an already-generated rewrite destination.

## Expected correction and validation
Choose and document the intended configuration contract, then wire the same origin through the actual image build/deployment path. If the setting is build-time, expose an explicit build input and pass it before `next build`; if it must be runtime-configurable, implement a runtime proxy mechanism rather than relying on a build-generated rewrite.

Add coverage that builds the canonical Dockerfile with the supported configuration and checks the produced proxy destination. Keep the intended missing-production-setting refusal, and verify that no private host is silently restored as a default. The new Python source-text checks do not exercise Next's production config loading or the Docker build.
