# Issue 1640: [P2] Reconcile orphaned acceptance replay jobs with price-feed retention

## Defect and impact

The retention gate added by [23b29a1488da2b8656fef7bb6bba6aaa9d5a05c2](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/23b29a1488da2b8656fef7bb6bba6aaa9d5a05c2) can remain closed after the replay runner reports completion. A durable replay job for a block that is no longer consensus is never selected by the runner, but it is still counted as pending by maintenance. With retention configured, one such row prevents expiration of all price-feed updates and observations, including unrelated eligible history.

Reviewed at e67d2f76f21d2ce58b3630967b0f0ab2c953b701 and rechecked against main at bc89ac92e6b057c652ed13ec42725107008ccbf9; the relevant source remains unchanged. This is an explorer retention/lifecycle defect, not a claim about chain replay, authorization, funds, or a deployed occurrence.

The FK removes a queue row only when its block is deleted.

This also applies when a queued canonical block loses consensus after migration.
- [Replay selection/completion](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/services/explorer/backend/apps/explorer/priv/repo/migrations/scripts/price_acceptance_backfill.exs#L52-L70): next_job selects only incomplete jobs with b.consensus=true; if none qualify, step returns :complete without retiring the non-consensus rows.
- [Pending predicate](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/services/explorer/backend/apps/explorer/priv/repo/migrations/scripts/price_acceptance_backfill.exs#L20-L23): counts every completed=false row, irrespective of current block consensus.

[The transient runner](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/services/explorer/backend/apps/indexer/lib/indexer/fetcher/paxeer_x/price_acceptance_replay.ex#L6-L6) [stops normally at :complete](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bc89ac92e6b057c652ed13ec42725107008ccbf9/services/explorer/backend/apps/indexer/lib/indexer/fetcher/paxeer_x/price_acceptance_replay.ex#L31-L43).

## Expected versus actual

Expected: replay completion, job eligibility and the retention guard agree on the lifecycle of non-consensus jobs. Historical rows needed by active canonical replay remain protected, while an orphan job cannot indefinitely suspend retention globally.

Actual: after all canonical jobs complete, step returns :complete and the runner exits, but pending? remains true indefinitely while the non-consensus block and queue row remain stored. Every maintenance pass therefore reports zero expired rows.

## Concrete validation plan (source-derived, not executed)

Extend Repair2231472Test using its real PostgreSQL and recorded-node fixtures:
1. Import a consensus legacy price-update block H older than the retention window and run migration 20261104000000, establishing its incomplete queue row.
2. Import a replacement consensus block at H through the normal block-import path so the original block remains stored with consensus=false. Also keep a separate expired canonical update with a newer accepted observation, ensuring unrelated history is eligible for expiration.
3. Complete any other canonical jobs, then call PriceAcceptanceBackfill.step/2. Current code returns :complete while pending?/0 is still true for the old block.
4. Call PriceFeedMaintenance.run_once/2 with retention enabled. It currently expires zero rows and leaves the unrelated eligible history intact. Verify that restarting the replay runner does not clear this condition.
5. Cover a block already non-consensus when migration runs, and a block losing consensus between replay batches.

## Acceptance criteria

- Explicitly reconcile orphan job retirement/deferment with queue completion and retention eligibility; do not replay a non-consensus block or mark it successfully requalified without evidence.
- No incomplete canonical job loses observations required for replay.
- Orphan jobs do not globally freeze retention, including after runner restart.
- If the design permits a retained block to regain consensus, define and test how its replay eligibility is restored.
- Add the producer-to-runner-to-maintenance regression above, preserving the existing durable cursor and canonical retention tests.
