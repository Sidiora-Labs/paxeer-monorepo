# Issue 1628: [P2] Apply virtual-chain scope to installed pending transaction filters

## Expected versus actual

The [virtual-chain RPC contract](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/spec/layerx-merge/contracts/virtual-chains.md#L101-L109) says installed filters restrict results to the chain's transactions, while root reads retain the full view.

On a server configured with a receipt feed, `eth_newPendingTransactionFilter` installed at `/chain/1` instead returns root and chain-2 hashes through `eth_getFilterChanges`. Those hashes are excluded by the same endpoint's scoped transaction reads. This is an API consistency defect: [virtual chains share EVM state and are explicitly not a trust boundary](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/spec/layerx-merge/contracts/virtual-chains.md#L89).

Verified statically at main `aefa91aa13a43dff9d0a27098f8280d43fd1ed42`. The underlying pending-filter behavior predates [a04ec978](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/a04ec978f9fb4157deb869e24848db0ba53742fb); that repair passes scope through the WebSocket wrapper but does not make the hash-filter consumer apply it.

## Producer and consumer evidence

- [The scoped wrapper supplies DomainScope](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/rpc/domain_ws_apis.go#L109-L120) to both installation and polling.
- [NewPendingTransactionFilter](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/rpc/filter.go#L877-L907) subscribes to the global receipt feed and creates a filter without saving `domainScope`.
- [ReceiptLogFeed.Receipted](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/rpc/filter.go#L298-L333) appends every receipted transaction to every installed feed filter.
- [GetFilterChanges](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/rpc/filter.go#L913-L988) scopes only log result types in its deferred handler. The pending-transaction branch drains the feed and returns every `tx.hash` as `[]common.Hash`, with no domain check.
- [The existing mixed-domain pending test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/aefa91aa13a43dff9d0a27098f8280d43fd1ed42/rpc/repair_339_test.go#L315-L425) exercises actual receipt production, scoped raw/ordinary lookups, counts and blocks on HTTP/WS, but does not install a pending-transaction hash filter.

## Reproduction / validation

Extend `TestRepair_339_TenantPendingRaw` using its existing root, chain-1 and chain-2 clients and real embedded executor:

1. After server startup, before the transaction-production loop, call `eth_newPendingTransactionFilter` with `false` separately on each root/chain-1/chain-2 HTTP and WS client. Keep the returned IDs.
2. Execute and receipt the fixture's four transactions in order: root, chain 1, chain 1, chain 2.
3. Poll each ID with `eth_getFilterChanges` on its installation path.
4. Expect all four hashes at root, only the two chain-1 hashes on chain 1, and only the chain-2 hash on chain 2. Current source returns all four for every filter.
5. Poll again and require an empty result. Reconnect the chain WS client within the filter timeout, receipt another mixed-domain batch, and require the same domain restriction when polling the retained ID.
6. Compare returned hashes with the ordinary scoped transaction lookup results.

This is a source-derived regression plan, not an executed test.

## Impact and acceptance criteria

Impact is conditional on pending-transaction filters being supported by the configured receipt feed. Nodes without that feed already refuse installation. A client watching a virtual chain currently receives unrelated transactions in its changes stream; no deployed incident, financial effect, confidentiality boundary or authorization bypass is asserted.

- Preserve the installation domain and apply it to pending hash results on HTTP and WS.
- Root filters retain the complete stream and receipt order.
- Successful polls consume the relevant stream once; reconnect does not change filter scope.
- Follow existing scoped-filter ownership behavior when an ID is queried from a different chain.
- Preserve explicit unsupported/full-transaction-mode refusals, overflow handling, expiry and uninstall cleanup.
- Add real mixed-domain producer-to-RPC regression coverage rather than testing only the wrapper.
