# Issue 1714: [P2] Resolve committed journey receipt references through evidence.get

## Problem
At main revision 4ff9c2a5fee18996de453c2bee13c2152be70ebf, a valid committed bank-journey receipt can be advertised by the Human API but rejected by its own evidence.get endpoint. This prevents clients from retrieving the receipt material referenced by a finalised journey.

## Source proof
- The [journey producer](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/src/journeys/engine.rs#L1811-L1828) retains authenticated commitment evidence and persists the receipt at Committed.
- The [journey projection](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/src/server/production_reads.rs#L1205-L1234) passes that actual rung to receipt_label_with_keys and emits evd_<receipt digest>.
- The [committed-label branch](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/src/server/production_reads.rs#L1314-L1336) checks the receipt digest and signature, verifies the retained bank commitment, and returns checkpoint-finalised.
- The [evidence.get consumer](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/src/server/production_reads.rs#L906-L921) finds the same journey receipt and invokes that label function, but accepts only receipt-verified. A valid Committed result therefore returns upstream_degraded before managed_receipt_material, even though [that exporter](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/src/server/production_reads.rs#L786-L820) explicitly supports a Committed label.

The mismatch was introduced by the committed-label integration in [f83425c2](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/f83425c2a8b990d50d884e286f59800c7de91252); the retrieval guard was left unchanged.

## Expected and actual
Expected: with valid receipt keys and retained commitment evidence, a receipt reference emitted for a committed journey resolves through the authenticated production evidence endpoint with consistent verification metadata and verifiable material.
Actual from the source path: the successful committed verification result is rejected solely because its label is checkpoint-finalised rather than receipt-verified.

## Validation
Extend the existing recorded bank-commit/reopened-store fixture to query journey.get and then dereference its emitted receipt evidence_id through the actual ProductionComponents::evidence_get path with configured receipt keys. The [current projection test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/4ff9c2a5fee18996de453c2bee13c2152be70ebf/services/human/crates/layerx-human-service/tests/projection_rungs.rs#L423-L486) checks journey/activity responses and labels but does not dereference those IDs.

Source inspection only: no repository test, live transaction or deployment check was executed. The failure described assumes the normal receipt-key and proof prerequisites succeed; earlier configuration failures are separate.

## Acceptance criteria
- Resolve valid Receipted and Committed journey receipt references without rejecting the latter's verified label.
- Preserve receipt signature, digest and retained commitment checks; do not fix this by weakening validation or overstating exported proof strength.
- Add production-endpoint coverage for both rungs, reopened stores, and absent or altered commitment evidence.
