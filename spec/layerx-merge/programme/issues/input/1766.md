# Issue 1766: [P3] Keep the legacy explorer block counter on height after websocket updates

## Defect and scope

Commit 213a42d6ac000615cc3f18c660413563cc8fbe7e changes the legacy chain page's initial block counter to the latest consensus block number. Its live JavaScript consumer still replaces that value with the size of the indexed range when the next block arrives.

This affects installations that enable the legacy WebRouter. It is not a claim about the separately deployed frontend: the checked configuration defaults to DISABLE_WEBAPP=true, and the deployment example also disables this page.

## Reproduction by source trace

With legacy WebRouter enabled and indexer first_block = 100:

1. A page rendered at consensus height 500 shows 500.
2. A new_block event for block 501 reaches the reducer.
3. The counter becomes (501 - 100) + 1 = 402.
4. Reloading the page shows 501.

For first_block = 0, the live value is instead one above the block number. These are deterministic consequences of the current reducer; no browser, test suite or deployed service was exercised for this report.

## Expected behavior and repair

Keep the initial HTML and live update on the same latest-consensus-height contract. Update the legacy reducer accordingly, including its handling of older or replacement block notifications, and add a regression covering initial render followed by a real-shaped socket message with zero and nonzero first_block values.

The new repair_22_35_9 tests assert controller responses and initial HTML only, so they do not cover this transition.
