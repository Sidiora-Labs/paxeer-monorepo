# Issue 1587: [Coherence] The blocking reward-request-schema finding claims l18_requests and l18_audit have no production schema, but the reviewed launchpad migration registry declares both for the pnl-tracker

## Defect and impact

The audit record marks the package not upgrade-ready. One of its two blocking high findings says that no checked-in schema, legacy migration or launchpad deployment SQL declares the l18_requests and l18_audit tables. In fact, launchpad/spec/production-system/integration/migrations/180001.sql creates both tables in schema "pnl", and registry.json registers that migration for core/pnl-tracker under owner lane L18. The production coordinator loads migrations from this same registry. Because the finding is false, its proposal to add new migrations for these tables would duplicate an existing registered migration, and upgrade_ready=false rests partly on a defect that does not exist. The related medium finding reward-proof-schema also stands on the wrong premise: the proof test builds the tables by hand instead of applying 180001.sql, but the production schema itself is not missing.

Kind: semantic. Severity: major.

## Expected versus actual

Expected: The record should recognise that 180001.sql in the registered migration set declares l18_requests and l18_audit.
