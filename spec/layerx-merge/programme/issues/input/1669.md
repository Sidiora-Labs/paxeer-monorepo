# Issue 1669: [Coherence] Resuming after an aborted refresh fails permanently once the journal has rotated to a new refresh session

## Defect and impact

When members report an aborted refresh, prepareRefreshRecovery moves the old session into RefreshRecoverySession, sets a new RefreshSession and saves the journal. The resume paths now call InspectRefreshRecovery with only c.RefreshSession, and that check rejects any member whose recorded refresh SessionID differs from it. If the run stops after this rotation is saved but before every member has run the replacement attempt (a crash, or one member's RefreshCeremony failing), the members still hold the old aborted session. Every later resume then returns ErrDisagree before it gets to the replay. Before this commit, DescribeCeremony was used here, so the resume reached RefreshCeremony with the recovery session and completed.

Kind: semantic. Severity: major.

## Expected versus actual

Expected: When RefreshRecoverySession is set, recovery inspection should accept members whose recorded attempt is that aborted session (state aborted, decision abort, base epoch), or should skip the strict inspection, so the resume can replay the refresh with the recovery session.

Actual: After the rotation is saved, any interruption leaves members holding the old aborted session. Each resume then fails in InspectRefreshRecovery with ErrDisagree, and the wallet can never finish migrating without editing the journal by hand.
