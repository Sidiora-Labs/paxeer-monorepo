# Issue 1654: Subscription over-delivery test uses cumulative count after notifications are consumed

## Problem

At [ca9cf1b](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/ca9cf1b9456be6be3de2bbf2720b4556228da5d8), [`WsClient.waitFor`](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/ca9cf1b9456be6be3de2bbf2720b4556228da5d8/tests/integration/rpc_tests/utils/subscribeUtils.ts#L139-L152) removes the returned notifications from its buffer. After consuming the expected N logs, the [subscription integration test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/ca9cf1b9456be6be3de2bbf2720b4556228da5d8/tests/integration/rpc_tests/eth/eth_subscribe.spec.ts#L175-L190) still waits for N+1 notifications to detect over-delivery. The consuming behavior was introduced in [9fe6328a](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/9fe6328a30a9843787f4f20503b426b35e92f438).

## Expected versus actual

After the expected logs have been consumed, a single additional matching notification should fail the no-over-delivery assertion. Instead the guard waits for N+1 *additional* notifications; one through N extra logs can be missed when the wait times out. This weakens the integration test and does not by itself establish a production subscription defect.

## Validation

Use a deterministic mock or test server to deliver N expected logs and one extra notification for the same subscription. Confirm that the current guard times out and passes; after the fix it should fail. Also verify exactly N deliveries pass and that unrelated subscription notifications do not trigger a false failure.

## Acceptance criteria

- Make the over-delivery assertion consistent with consuming buffer semantics, detecting even one extra matching notification.
- Add regression coverage for exactly N, N+1, and unrelated-subscription delivery.
- Preserve correct behavior for other callers of `waitFor`.

Source inspection only; validation was not executed.
