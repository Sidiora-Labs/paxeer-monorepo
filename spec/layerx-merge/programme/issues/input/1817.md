# Issue 1817: Fix sparse-workspace qualification's explicit-profile IPC mismatch

## Summary

The sparse-workspace qualification still accepts `HYPERFIDE_SOURCE_CONTROL_TEST_PROFILE`, but the new revocation case depends on an IPC control channel that only the owned fixture provides. The explicit-profile launch path cannot complete that case.

Introduced by fdb5915e70bf2b61955af6f5d3bf1fa5363ddafc and verified statically at main `bedd71ff1d52a89329be5be9c6a95b7667fe5412`. This is a qualification-launcher incompatibility, not a production authorization-bypass finding. No test or external service was executed during this review.

## Producer/consumer mismatch

1. [The explicit-profile branch at 2_2.py:247–255](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/tools/hyperfide/tests/hyperfide/cases/source_control/2_2.py#L247-L255) runs the JavaScript program directly with Python `subprocess.run`. It creates no Node IPC channel or parent message handler.
2. [serverControl at lines 39–44](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/tools/hyperfide/tests/hyperfide/cases/source_control/2_2.py#L39-L44) rejects with `CAPABILITY_MISSING` when `process.send` is absent.
3. [The new unconditional case at lines 142–158](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/tools/hyperfide/tests/hyperfide/cases/source_control/2_2.py#L142-L158) first requires `profile.revocation_token`, then calls `serverControl('revoke-checker')` after the first object read. Its assertion expects `SCOPE_DENIED`, not `CAPABILITY_MISSING`.
4. [Only native_source_sparse_fixture.mjs:54–80](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/tools/hyperfide/tests/hyperfide/support/native_source_sparse_fixture.mjs#L54-L80) launches the child with `stdio: [..., 'ipc']` and handles that control request.

Consequently, an ordinary explicit profile fails at the missing revocation-token assertion. Adding a valid separate token still cannot supply the missing parent IPC handler: when the case reaches its first object read, the control call fails with the wrong error. Later checkpoint and widening cases are not reached on that route.

## Suggested resolution

Make the two launch modes and the qualification requirements agree. Either provide an explicit-profile control adapter with a documented contract, or reject that mode before creating fixture data and direct callers to the owned fixture. If a reduced external-profile suite is intentional, report its limited coverage clearly instead of treating it as full qualification; do not silently skip the required revocation proof.

Add a launcher-level regression for both unset and set `HYPERFIDE_SOURCE_CONTROL_TEST_PROFILE`, including profiles with and without the control capability. Assert that the supported route reaches the later cases and that unsupported capabilities are reported before source-service writes.
