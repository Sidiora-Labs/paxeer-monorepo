# Issue 1582: [P2] Align Python ProgramOperations input with EVM receipt verification

## Problem

At [b4bbe0b](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a), the public [ProgramOperations.submit](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a/services/agent/sdk/python/layerx_sdk/programs.py#L375-L395) first decodes and retains a legacy signed-program envelope. Its [parser](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a/services/agent/sdk/python/layerx_sdk/program_wire.py#L132-L164) requires a u16 version 1/2/3. The [receipt adapter](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a/services/agent/sdk/python/layerx_sdk/programs.py#L438-L475), updated in [be40a6fb](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/be40a6fb), passes those same bytes to an [EVM decoder](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a/services/agent/sdk/python/layerx_sdk/evm_transaction.py#L100-L105) requiring type 0x02. These formats cannot both match. The [daemon submission path](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/b4bbe0b5a4ba8e3cbaafc5198f1ec7d20dafe66a/services/agent/crates/layerx-agentd/src/ops/program.rs#L1690-L1731) consumes EVM bytes.

## Expected vs actual

Expected: the public SDK accepts the supported producer transaction and verifies its returned receipt against those exact bytes. Actual: EVM input fails legacy decoding before submission; legacy input cannot pass the EVM receipt adapter, so a successful response cannot be verified through this public path and becomes unknown. New positive tests exercise private adapters directly with EVM bytes, bypassing the public input boundary. This is a source-level incomplete migration, not a demonstrated deployment incident.

## Validation

Add a producer-backed test invoking the public `ProgramOperations.submit` with a valid type-2 program transaction and a matching signed sequencer receipt. Verify exact transaction identity, successful receipt verification, and refusal for altered bytes. Include the lifecycle path or explicitly retire it if unsupported. Static analysis only; no test or live submission was executed. Full aggregate spec was unavailable, so active task ownership could not be exhaustively checked.

## Acceptance criteria

- Public input, daemon request and receipt verification use a consistent supported transaction and identifier contract.
- Public positive and tamper/refusal tests exercise the entire boundary rather than only a private helper.
- Retained lifecycle/recovery behavior is explicitly aligned or retired without weakening receipt authentication.
