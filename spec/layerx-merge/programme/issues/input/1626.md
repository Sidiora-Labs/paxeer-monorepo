# Issue 1626: Staking redelegation query erases sparse-page continuation after scan cap

Destination-filtered redelegation queries can report the end of pagination even when later matching redelegations remain.

**Expected:** Preserve a continuation when the scan limit is reached, or return an explicit limit error.

**Actual:** On a keyless request, queryAllRedelegations overwrites the raw paginator continuation with nextMatchingKey. If the scan cap is reached before another matching item reaches the callback, nextMatchingKey is nil and the valid raw continuation is lost.

Source at the rechecked main commit:

- Destination-only requests use the all-redelegations path: https://github.com/Sidiora-Labs/paxeer-monorepo/blob/174f8416e84e2dde4f8c2bffab6d1d3f6597d0a2/sdk/x/staking/keeper/grpc_query.go#L397-L400
- The callback and overwrite: https://github.com/Sidiora-Labs/paxeer-monorepo/blob/174f8416e84e2dde4f8c2bffab6d1d3f6597d0a2/sdk/x/staking/keeper/grpc_query.go#L550-L580
- The paginator scan cap and raw continuation: https://github.com/Sidiora-Labs/paxeer-monorepo/blob/174f8416e84e2dde4f8c2bffab6d1d3f6597d0a2/sdk/types/query/filtered_pagination.go#L102-L146

**Source reproduction:** Request destination D with limit 1, count_total false, and no key. In key order, place a match for D first, then 10,001 nonmatches, then another match for D. After filling the page, the paginator reaches its scan cap and returns the next unprocessed raw key before calling the filter on it. No subsequent match reached the callback, so nextMatchingKey remains nil and the caller replaces the raw key with nil. The client receives success and no next_key, silently missing the later match.

**Verification:** An independent Python control-flow model with 10,003 rows reproduces this result. The source paths were rechecked at the linked commit; repository Go tests and deployed behavior were not tested.
