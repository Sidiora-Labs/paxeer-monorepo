# Issue 1770: Explorer Ask flag is rejected by the startup environment validator

## Impact

The Ask change adds `NEXT_PUBLIC_ASSISTANT_ENABLED` to the shipped Paxeer preset and documents enabling it, but the production environment validator never includes the new `assistantSchema`.

An otherwise valid frontend deployment supplying this flag, whether `true` or `false`, fails validation and exits before Next.js starts. This includes the documented Paxeer preset when installed as `.env.paxeer-x` with normal environment validation enabled, even though Ask is disabled there.

Introduced by [18fc77a5](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/18fc77a542d2c20d4e27e3d06f2f03252367e29c). Rechecked on main `7906898fca65b0738a8b94edcc622f01388f61c2` at 2026-11-06 12:23 UTC.

## Reproduction and expected behavior

Source-derived reproduction, not executed: start the normal frontend image with otherwise valid settings and `NEXT_PUBLIC_ASSISTANT_ENABLED=false` or `true`, with environment validation enabled. The aggregate validator rejects this key as unknown, and startup terminates before `node server.js`.

Both valid boolean values should pass the actual deployment validator. Register the assistant feature schema in the relevant aggregate schema rather than weakening unknown-variable validation.

Suggested regression checks:

1. Complete valid production settings with the flag `true` and `false` are accepted.
2. An invalid boolean value is rejected.
3. The documented Paxeer preset passes the validator.
4. An unrelated unknown public variable remains rejected.
