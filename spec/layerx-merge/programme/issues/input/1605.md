# Issue 1605: [Coherence] The image-build-context finding misstates the Docker build context, so its proposed repair targets the wrong cause

## Defect and impact

The audit record says both image targets in sdk/contrib/images/Makefile use sdk/ as their build context and fail because sdk/go.mod is absent. In fact the context is $(abspath ../../..), which from sdk/contrib/images resolves to the repository root, where go.mod exists. The images really fail because the Dockerfiles copy root-relative ./ics23/go.mod and contrib/... paths, and those only exist under sdk/. The companion environment-image-build finding repeats the same wrong premise ('an sdk-root context with no go.mod'), so a repair task built from these findings would move the context to a root it already uses instead of fixing the COPY paths.

Kind: semantic. Severity: minor.

## Expected versus actual

Expected: The findings should say the build context is the repository root, and that the COPY paths ./ics23/go.mod and contrib/images/... (plus the absent build/simd output) don't match the sdk/ics23 and sdk/contrib layout.

Actual: The record blames an sdk/ build context with no go.mod. It proposes porting the Makefile to the root build, but the Makefile already uses the root.
