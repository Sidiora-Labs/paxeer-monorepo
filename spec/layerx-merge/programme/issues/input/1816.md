# Issue 1816: Reconcile ask-stream ID types in the inference contract and protocol guide

## Summary

The ask-stream implementation landed in 41d32cc012181c9d27889efabefa64e2170c3882, but the inference-market contract catalogue and protocol guide still describe a different stream-ID ABI. Please reconcile these documents with the implementation before consumers derive bindings or event filters from them.

Verified at main `bedd71ff1d52a89329be5be9c6a95b7667fe5412` on 2026-11-07. This is a static documentation/interface mismatch. The documents explicitly label these APIs planned; no deployed consumer failure or runtime incident is claimed.

## Evidence

- [Contract catalogue, lines 130–132](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/spec/layerx-merge/contracts/inference-market.md#L130-L132) says `streamOpenForAsk(...)` and `askStreamOf(bytes32)` return `uint64`, and declares `AskStreamOpened(bytes32 indexed,uint64 indexed,address)`.
- [Protocol guide, lines 117–120](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/docs/agent/inference-market/protocol.md#L117-L120) repeats the `uint64` return types.
- [Implementation ABI, lines 103–104](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/precompiles/layerxpay/abi.json#L103-L104) returns `bytes32` for both methods. [The event at line 187](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/precompiles/layerxpay/abi.json#L187) has a `bytes32` indexed stream ID.
- [Go handler, lines 22–47](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/precompiles/layerxpay/stream.go#L22-L47) packs the native 32-byte ID directly. [The existing regression source, lines 237–242](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/bedd71ff1d52a89329be5be9c6a95b7667fe5412/precompiles/layerxpay/stream_ask_test.go#L237-L242) explicitly expects `AskStreamOpened(bytes32,bytes32,address)`.

## Why the mismatch matters

Return types do not change a function selector, so a consumer can call the right selector while using the wrong output decoder. A native 32-byte ID is not a generally valid `uint64` output. The two event signatures also produce different topic-zero hashes, so the planned catalogue would generate an incompatible event filter. These are consequences of the conflicting definitions, not evidence that such a consumer has shipped.

## Suggested resolution and verification

Reconcile the owner-approved contract with the landed native stream-ID representation. If the existing `bytes32` representation is intended, update both documents and the event signature together; if `uint64` remains intended, define the explicit mapping rather than silently changing the native ABI.

Add a contract check comparing the catalogue/protocol method outputs and event signature with `precompiles/layerxpay/abi.json`. Keep the planned/unqualified status where appropriate. No test was executed during this review.
