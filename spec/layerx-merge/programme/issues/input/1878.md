# Issue 1878: Live campaign can promote task-component evidence to full-case PASS

Affected revision: 0edc903b4a4120ea145e68acb1a9712c54d7976a; introduced in acbbb018ff1601c1509473636701c2cdeb4b8080.

Expected
The live campaign must execute the full-case variant listed for each admitted manifest and record PASS only for its complete checked assertion inventory. The runner itself selects only full-case registrations (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/support/source_control_live_campaign.py#L114-L120). SCM-024 explicitly names case:hyperfide-source-control/SCM-024/full, verifier-scm-024.json and the registry full_assertion_ids (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/spec/layerx-merge/source-control/live-campaign.kvx#L384-L397).

Actual
The inventory checks the expected manifest filename exists but does not bind its contents to the expected variant (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/support/source_control_live_campaign.py#L153-L173). Execution passes only --case SCM-024; qualify.py selects the registration from manifest.registered_variant and checks case membership (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/qualify.py#L845-L855). A valid task 0.2 component manifest names SCM-024 and has 20 assertions, versus the full case's 60. Successful component qualification intentionally returns exit 0 while its full_case_status is INCOMPLETE (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/qualify.py#L761-L797). The new wrapper turns exit 0 into PASS (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/support/source_control_live_campaign.py#L191-L209) and writes that status into the private case registry without checking scope, variant or full-case outcome (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/support/source_control_live_campaign.py#L248-L258).

Reproduction
1. Prepare a valid current task:hyperfide-source-control/0.2 manifest, with its actual native capture, source/toolchain pins and approval, using the existing 0.2 registration (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/source-control/registrations/0.2.json).
2. Place that manifest at $HF_SOURCE_LIVE_CAMPAIGN_MANIFESTS/verifier-scm-024.json rather than the expected full-case manifest. No change to its contents is needed.
3. In an otherwise correctly provisioned owned campaign environment, from tools/hyperfide run python3 tests/hyperfide/cases/source_control/sparse_live.py. The SCM-024 manifest is admitted, and qualify.py --case SCM-024 selects task 0.2.
4. If the component and checker succeed, inspect its full_case_status INCOMPLETE and the private live campaign registry's SCM-024 status PASS.

Verification performed
An isolated Python execution of the exact AST-extracted validate_manifest accepted the component manifest against the pinned 0.2 registration and registry: 20 component assertions, 60 required full-case assertions. This used synthetic nonsecret inputs solely to exercise pure contract validation. No real native capture, qualifier, checker, S3, database or live campaign was run. Steps 3-4 describe the source-supported consequence of an actual successful component run, not an observed live test.

Impact and boundary
The private live-campaign inventory can falsely advertise that its requested full-case variant passed. The existing release closure independently rejects component scope and requires the exact variant and full_case_status PASS (https://github.com/Sidiora-Labs/paxeer-monorepo/blob/0edc903b4a4120ea145e68acb1a9712c54d7976a/tools/hyperfide/tests/hyperfide/source-control/closure.py#L140-L157), so this report does not establish a release bypass, production incident, security exploit or funds impact.

Acceptance
- Bind every supplied manifest to the expected full-case registration, exact case and complete assertion inventory before launch.
- Check the actual independently verified receipt's scope, variant, case, source identity and full_case_status before promoting its status.
- Add negative cases for a valid component manifest under a full-case filename and one full-case variant reused for multiple required variant filenames. Preserve all existing checker and full-case assertions.
