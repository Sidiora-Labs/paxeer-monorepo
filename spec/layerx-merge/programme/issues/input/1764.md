# Issue 1764: [Coherence] Committed waits rebuild the batch's activity list from eth_getBlockByNumber, but the node's block view is a filtered subset of the transactions the sequence batch counts, so genuine committed receipts are refused

## Defect and impact

The new from_sequence_batch takes the ordered activity IDs from the `transactions` array of eth_getBlockByNumber(height, false) and requires its length to equal to_sequence - from_sequence + 1. On the node, the batch covers every transaction after tx 0: sequencedActivityIDs hashes each one, using the EVM hash or sha256 of the raw bytes. The eth block encoder, however, drops associate txs, ante-failing and non-nonce-bumping EVM txs, shell synthetic receipts, wasm executes (unless synthetic txs are included), bank sends (unless enabled), undecodable txs and every other Cosmos message, and it filters further under a domain scope. Any committed block holding one of these makes the count or sequence position disagree, and the SDK returns RpcError::Verification for a receipt the chain really committed. The loopback fixtures cannot catch this, because they serve exactly one activity per block.

Kind: cross-system. Severity: major.

## Expected versus actual

Expected: Per-wait coverage should be built from an activity-ID list the node serves exactly as the batch commits it: every tx after tx 0 in block order, EVM hash or sha256 of the raw bytes. For example, the full Comet block txs, or a px_getSequenceBatch field carrying the IDs.

Actual: Coverage is built from the filtered EVM-facing eth_getBlockByNumber hash list. A committed block that also holds any non-listed transaction makes the length or position check fail, and the wait returns Verification.
