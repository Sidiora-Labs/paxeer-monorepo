# Issue 1820: [P2] Preserve ECR dispatch input identity in the concurrency group

## Problem

The push-concurrency change also removes `inputs.ref` and `inputs.tag` from the Paxeer / ECR manual-dispatch group. Two independent image requests dispatched from the same workflow branch now share a cancellation group, even when they request different source refs or output tags.

When the workflow and publisher are enabled, a second dispatch can cancel an in-progress first dispatch before its requested image set finishes. The publisher is conditional on `AWS_ECR_ROLE_ARN`; current activation/configuration and live cancellations were not verified.

## Static reproduction

For two `workflow_dispatch` events with `github.ref=refs/heads/main`:

1. Request source ref A with image tag A.
2. While the first run is in progress, request source ref B with image tag B.

Both groups evaluate to `Paxeer / ECR-workflow_dispatch-refs/heads/main`. Their old groups differed. The second request therefore supersedes the first despite its different checkout/publication target. The input names here illustrate valid distinct requests, not existing repository refs.

## Acceptance criteria

- Preserve SHA isolation for push events and current PR cancellation behavior.
- Retain manual dispatch source/tag identity, or otherwise avoid cancelling independent manual requests.
- Cover two differing dispatch inputs in a regression test. The [current test](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/fdfd0efa047fa7ab98fb25b8c407db351b566fff/tests/ci/test_workflow_push_concurrency.py#L6-L9) requires one identical expression across the workflows and does not test dispatch input identity.

Validation was static source inspection and expression evaluation only. No workflow was triggered, image built, or AWS operation performed. All-state issue/PR searches found no matching report; #1786 concerns readiness counts and #773 concerns a historical native build.
