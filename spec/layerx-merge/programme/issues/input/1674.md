# Issue 1674: [Coherence] The interop messages HTTP API still emits and decodes a two-field cursor, so the page-boundary fix never reaches production paging

## Defect and impact

The commit adds a four-field cursor to the explorer module: `InteropMessage.paging_params/1` and `paging_options/1`, plus a four-tuple `page_messages` clause. Nothing in the request path calls them. `/api/v2/optimism/interop/messages` still builds `next_page_params` from `BlockScoutWeb.Chain.paging_params/1`, which sends only timestamp and init_transaction_hash. `BlockScoutWeb.Chain.paging_options/1` still decodes a `{ts, hash}` two-tuple, and that goes to the legacy two-field `page_messages` clause. So any page that ends partway through a multi-message transaction still skips the remaining messages, which is the exact defect audit finding interop-page-boundary describes. Malformed cursors also still fall back silently to the first page instead of failing. The commit's own repair record admits this wiring is missing. The repair test passes only because it calls the new explorer functions directly instead of driving the controller.

Kind: connective. Severity: major.

## Expected versus actual

Expected: `/api/v2/optimism/interop/messages` should emit the four-field cursor and decode it with `InteropMessage.paging_options/1`, rejecting invalid cursors, so paging visits every message exactly once.

Actual: The explorer module has the four-field cursor, but the API still sends and parses two fields. Messages that share a transaction at a page boundary are still skipped, and bad cursors still silently restart from the first page.
