# Issue 1871: [P2] Follow the composite release toolchain in the compiler-pin test

## Problem
Commit [775a34c6](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/775a34c6ff79efe75976ba3dba4d1ea2376f7802) moved the native compiler setup into a local composite action, but the retained release test still reads the caller step's `run` field. Both callers now have `uses` instead, so `check_pins_cc()` raises `KeyError: 'run'` before it can inspect or test the compiler pin.

Verified against current `main` [26703a14](https://github.com/Sidiora-Labs/paxeer-monorepo/commit/26703a14fdc91d391e9253aec25f0f83e529968c) on 2026-11-08 at 03:44 UTC.

## Source
- [Release-check caller](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/26703a14fdc91d391e9253aec25f0f83e529968c/.github/workflows/paxeer-release-check.yml#L93-L98) and [release-publish caller](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/26703a14fdc91d391e9253aec25f0f83e529968c/.github/workflows/paxeer-release-publish.yml#L51-L56) use `./.github/actions/release-toolchain`.
- [The test helper](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/26703a14fdc91d391e9253aec25f0f83e529968c/tools/release/tests/workflows.test.sh#L31-L41) unconditionally returns `entry["run"].strip()`.
- [check_pins_cc](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/26703a14fdc91d391e9253aec25f0f83e529968c/tools/release/tests/workflows.test.sh#L82-L90) passes both native-dependency caller steps to that helper.
- [run-all.sh](https://github.com/Sidiora-Labs/paxeer-monorepo/blob/26703a14fdc91d391e9253aec25f0f83e529968c/tools/release/tests/run-all.sh#L20-L24) retains this script in the release test suite.

## Expected versus actual
Expected: compiler setup coverage follows the composite action and still checks the pinned compiler, its failure behavior, and caller ordering.
Actual: the test crashes on the first caller's missing `run` field; the action's compiler checks are never reached.

## Reproduction and validation
With Python 3 and PyYAML, run:
```sh
bash tools/release/tests/workflows.test.sh
```
The relevant output is `FAIL check_pins_cc: 'run'`.

To isolate this failure from other existing assertions:
```sh
python3 - <<'PY'
from pathlib import Path
source = Path("tools/release/tests/workflows.test.sh").read_text()
definitions = source.split("python3 - <<'PY'\n", 1)[1].split("\npassed = 0", 1)[0]
scope = {}
exec(definitions, scope)
scope["check_pins_cc"]()
PY
```
This raises `KeyError: 'run'`.

The script and isolated check were executed locally using a scratch tree of the pinned repository inputs. The full script reported 2 passed and 5 failed; only the compiler-step error is attributed here. At the prior inventory base `3615c117`, the caller had a `run` body; at this head it has only the local-action `uses` field. No release build or workflow execution was performed.

## Impact
The retained release regression suite remains failing even after its older version/grep assertions are repaired, and its compiler-pin validation no longer reaches the real setup implementation. This does not establish a failure of the actual compiler installation.

## Acceptance criteria
- Resolve and inspect the composite action used by both callers.
- Preserve the checks that installation precedes build and is unconditional/fail-closed.
- Keep positive and negative compiler-version checks against the action's implementation.
- The isolated `check_pins_cc()` check passes at the repaired revision.
- Mutations that remove or alter compiler pin/refusal behavior still fail the test.
