# Issue 1806: [Coherence] The receipt verifier still drops every pinned key whose id is not the SHA-256 digest of its public key, so the configuration change accepts keys that verification then ignores

## Defect and impact

The commit moves key parsing into ReceiptKeysConfig.parse/1, which follows the chain rule and no longer requires keyId to equal sha256(publicKey). It does not touch governed_keys/1 in SequencerReceipt, which still filters configured pins with `:crypto.hash(:sha256, public) == id`. With a merge plan whose key ids are not digests (the case decision 2754 targets), the explorer now boots, but every pin is filtered out, governed_keys returns {:error, :untrusted_receipt_keys}, and every receipt fails at step r3. The old boot-time refusal has become a silent failure for every receipt.

Kind: semantic. Severity: major.

## Expected versus actual

Expected: Every place that consumes the governed receipt keys applies the chain rule. governed_keys/1 should not require keyId to equal sha256(publicKey), so receipts signed under a non-digest key id verify.

Actual: Only runtime.exs was changed. governed_keys/1 still enforces the digest relation, so a configuration that now boots verifies no receipts and returns untrusted_receipt_keys for each one.
