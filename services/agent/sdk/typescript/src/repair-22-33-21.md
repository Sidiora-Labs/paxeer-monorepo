## Replay contract

`STREAM_REPLAY_WINDOW` is 1024 acknowledged events. Event IDs must contain 1–512
UTF-16 code units, so retained duplicate state is bounded in both count and size.
Duplicate IDs in the current page or the window at page admission are refused.
Validation is atomic for each page, including pages larger than the window.
The window advances only as events are acknowledged/delivered; `accept` explicitly
acknowledges the entire page. `retainedEventCount` exposes the current count.
IDs older than the window may recur with new continuous cursors. All page and
event cursor continuity checks remain mandatory. Reopening from a saved cursor
starts a fresh duplicate window; durable resumption depends on the source's
cursor continuity, as before. Applications needing lifetime ID uniqueness must
enforce it at the durable event producer.

## Web-search migration

Remove `authority` and `protocolVersion` entirely from client options. Supplying
either property now throws `obsolete-trust-configuration` at construction.
Configure a nonempty `receiptKeys` array of 32-byte key IDs and Ed25519 public
keys with inclusive u64 `first_height`/`last_height` ranges. Omitted/empty pins
throw `receipt-keys-required`; malformed pins throw `invalid-receipt-key` before
network I/O. Pins are copied at construction to retain the admitted trust policy.

An exact payer must return nonempty `rawTransaction` bytes alongside its signed
`receipt`, plus the idempotency key when applicable. Missing/empty bytes throw
`exact-raw-transaction-required` immediately after payer preparation and before
receipt verification or sending a payment header. Persist the raw transaction
when submitting payment, then return those exact bytes; do not reconstruct it.
The optional property declarations and deprecated options remain for compilation
of existing consumers during migration; they do not make these inputs usable at
runtime. No authority callback or version override can bypass pinned signature,
height, raw-transaction, payment or settlement checks. Metered settlements still
obtain raw bytes from the response or ledger RPC and pass the same pinned verifier.

The test serves the committed seller challenge and exact settlement over loopback
HTTP, checks the emitted payment header against the recording, replays recorded
ledger account RPC results, and exercises valid and forged signed receipts.
